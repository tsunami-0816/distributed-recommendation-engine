### 1.2 版本选择理由详述

#### 1.2.1 Java 17 + Spring Boot 3.2.x

- **Java 17**：LTS 版本，Oracle 支持至 2029 年；密封类、模式匹配、增强型伪随机数生成器；Spring Boot 3.x 最低要求。
- **Spring Boot 3.2.x**：基于 Spring Framework 6.1，支持虚拟线程（`spring.threads.virtual.enabled=true`），IO 密集型推荐接口吞吐量显著提升；启动速度较 2.x 提升约 30%。
- **关键依赖版本对齐**：
  - Spring Framework 6.1.x
  - Spring Data MongoDB 4.2.x
  - Spring Data Redis 3.2.x（Lettuce 客户端）
  - Spring Data Elasticsearch 5.2.x
  - MyBatis-Plus 3.5.5（MySQL 访问层）
  - Kafka Clients 3.6.x
  - gRPC 1.59.x（模型推理服务调用）
  - **Resilience4j 2.x（resilience4j-spring-boot3）**：限流、熔断、重试一体化
  - **Guava 32.1.x（仅用于 Hashing.murmur3_32，A/B 分流）**

#### 1.2.2 Spark 3.5.x（本地模式）

- 支持 `spark.master=local[*]` 单机多线程运行，集群迁移时仅修改 master 地址为 `yarn` 或 `k8s://...`。
- 自适应查询执行（AQE）默认开启，本地模式下自动优化 Join 策略与分区数。
- **本地模式配置简化**（修复 P0-01）：
  - 仅保留 `spark.driver.memory=4g`（本地模式所有任务运行在 driver JVM 中）
  - **删除 `spark.executor.memory` 配置**（本地模式下该参数无效，会误导开发者）
  - `spark.sql.shuffle.partitions=8`、`spark.adaptive.enabled=true`

#### 1.2.3 Flink 1.18.x（本地模式）

- `StreamExecutionEnvironment.createLocalEnvironment()` 启动本地执行环境，无需搭建集群。
- **采用 at-least-once + 消费端幂等去重**（降低实现复杂度，配合幂等性设计见 4.2/4.3）。
- 状态后端 `HashMapStateBackend`，Checkpoint 间隔 30 秒，存储本地文件系统。
- **统一事件时间语义**（修复 P1-02）：使用行为事件时间戳 + `BoundedOutOfOrdernessWatermarks(Duration.ofSeconds(5))`，删除 ProcessingTimeTimer，避免乱序行为导致计数错误。
- **窗口模型重构**（修复 P1-02）：
  - 实时计数：**1 分钟滚动窗口 + `AggregateFunction`**（增量聚合，每窗口仅维护 3 个 long 计数器，不存储原始事件）
  - 1 小时聚合：应用层累加最近 60 个 1 分钟窗口结果，Flink 不再维护 1 小时窗口

#### 1.2.4 Kafka 3.6.x（KRaft 单节点）

- KRaft 模式消除 ZooKeeper 依赖，单机部署仅需一个进程。
- 关键配置：`num.partitions=3`、`default.replication.factor=1`、`log.retention.hours=168`。
- **生产者配置统一**（修复 P1-10）：
  - `acks=all`（与全局一致，不再为行为采集接口单独设置 `acks=1`）
  - `enable.idempotence=true`（幂等生产者，防止重试导致重复）
  - `compression.type=lz4`
  - `retries=Integer.MAX_VALUE`、`max.in.flight.requests.per.connection=5`（幂等模式下安全）
- 消费者：`enable.auto.commit=false`，处理完成后手动提交；`isolation.level=read_committed`。

#### 1.2.5 Elasticsearch 8.11.x（单节点）+ IK 分词器 + Embedding

- 单节点配置：`discovery.type=single-node`、`xpack.security.enabled=false`。
- **IK 分词器安装**（修复 P1-04）：
  - 安装命令：`./bin/elasticsearch-plugin install https://get.infini.cloud/elasticsearch/analysis-ik/8.11.0`
  - 验证：`GET /_analyze {"analyzer":"ik_smart","text":"测试分词"}`
  - Docker Compose 部署时基于 `elasticsearch:8.11.0` 构建自定义镜像（Dockerfile 内预装 IK 插件）
  - **降级方案**：IK 安装失败时使用内置 `standard` 分析器（按字切分，效果差但可运行），文档中标注为降级方案
- **Embedding 生成方案**（修复 P1-05，采用方案 A）：
  - 物品 embedding：离线批量生成，输入 = `物品名称 + 描述 + 标签` 拼接文本，调用 `text2vec-base-chinese` 生成 768 维向量 → PCA 降维至 128 维
  - 查询关键词 embedding：在线调用同一模型（Python 推理服务 `/embed` 接口），保证与物品 embedding 同向量空间
  - 维度选择理由：128 维在 10000 物品规模下兼顾召回质量与 HNSW 索引性能；768→128 PCA 保留 ≥ 92% 方差
  - 更新机制：随离线任务每日更新（物品元数据变更时触发增量更新），写入 ES `item_index.embedding` 字段
  - 在线推理方案：模型推理服务（Python）暴露 `/embed` HTTP 接口（端口 8083），Java 推荐服务通过 HTTP 调用，超时 50ms
- 索引设计：物品索引 `item_index` 包含 `keyword`、`category`、`tags`、`embedding`（dense_vector, dim=128, cosine, HNSW）。
- 文本检索使用 BM25；语义召回使用 `knn` 查询（HNSW），满足 CORE-02 响应时间 < 50ms。

#### 1.2.6 Redis 7.2.x（单节点）

- 客户端选用 Lettuce（Spring Data Redis 默认），支持连接池与响应式 API。
- **缓存 Key 设计重构**（修复 P1-01 / P2-03）：
  - 推荐结果：`rec:result:{scene}:{userId}:{abGroup}:{modelVersion}`，**分层 TTL**（高频用户 10s / 普通用户 60s / 高频兜底 120s）
  - 用户长期画像：`user:profile:long:{userId}`，TTL 300s，**离线任务更新时失效**
  - 用户短期画像：`user:profile:short:{userId}`，TTL 5s，**不主动失效**（靠短 TTL 自然过期）
  - 热点物品信息：`item:info:{itemId}`，TTL 600s
  - A/B 分流标记：`ab:user:{userId}:{experimentId}:{configVersion}`，TTL = 实验结束时间
  - 实时行为计数（滑动窗口）：`user:action:{userId}:{actionType}`，使用 Sorted Set（ZADD 幂等）
- 序列化：Key 使用 StringRedisSerializer，Value 使用 GenericJackson2JsonRedisSerializer。

#### 1.2.7 MySQL 8.0.x

- 存储结构化数据：物品元数据、用户基础信息、A/B 实验配置、模型版本元数据、物品相似度、物品热度、特征一致性校验记录。
- 字符集：`utf8mb4`，排序规则 `utf8mb4_unicode_ci`。
- 引擎：InnoDB，所有表必须有自增主键或业务主键。
- 访问层：MyBatis-Plus 3.5.5，提供通用 CRUD 与分页插件；复杂查询使用 XML 映射文件。

#### 1.2.8 MongoDB 6.0.x（单节点）

- 存储半结构化数据：用户画像标签文档、用户行为明细。
- **画像集合设计**（修复 P2-05）：
  - `user_profile`：以 `userId` 为业务主键（唯一索引），文档内嵌 `tags`、`longTerm`、`shortTerm`、`updatedAt`、`version`
  - **更新原子性**：Flink 仅 `$set shortTerm` 字段，Spark 仅 `$set longTerm` 字段，**禁止全文档替换**
  - 使用 `upsert=true`，Flink/Spark 写入均带 `{upsert: true}` 选项
- 行为明细集合 `user_behavior`：
  - **幂等键设计**（修复 P1-08）：增加 `eventId` 字段（由 `userId + itemId + actionType + eventTime` 哈希生成），建立唯一索引 `{eventId: 1}`
  - Flink 写入使用 `insertOne` + 重复键忽略（`ordered=false` + 捕获重复键异常）
  - TTL 索引 `expireAfterSeconds=2592000`（30 天，满足 DATA-02）
- 写关注 `w: 1`，读关注 `primary`。

#### 1.2.9 算法模型选型

- **XGBoost 2.0**：
  - 支持 GPU 加速训练（`device='cuda'`），无 GPU 时自动降级 CPU。
  - 导出 ONNX：使用 `onnxmltools.convert_xgboost`，输入特征维度固定为 30+。
  - 目标函数：`binary:logistic`（CTR 预测）。
- **DeepFM（PyTorch 2.1 实现）**：
  - 自行实现 DeepFM 网络结构（FM 一阶 + FM 二阶交叉 + DNN 高阶交叉）。
  - 嵌入维度：稀疏特征 embedding_dim=16，连续特征直接拼入 DNN 输入。
  - 导出 ONNX：使用 `torch.onnx.export`，设置 `dynamic_axes` 支持动态 batch。
  - 优化器：AdamW，学习率 1e-3，Batch Size 1024，训练轮次 20（Early Stopping patience=3）。
- **模型推理服务**：
  - 独立 Python 进程（FastAPI + uvicorn + gRPC 服务），加载 ONNX Runtime。
  - Java 推荐服务通过 gRPC 调用，接口定义 `PredictRequest`（特征向量 + 模型标识）→ `PredictResponse`（预测分数列表）。
  - **端口统一**（修复 P2-02）：gRPC 50051，**HTTP 健康检查 8082**（与第一轮 P2-02 报告一致，避免与 Flink Web UI 8081 冲突）
  - **Embedding HTTP 接口**：8083，提供 `/embed` 接口供搜索场景在线向量化

#### 1.2.10 特征一致性保障（新增，修复 P1-03）

- **特征计算引擎 `feature-engine` 模块**：
  - 单独工程，提供 Java 和 Python 双语言实现
  - 离线训练（Spark/Python）通过 Py4J 网关调用 Java 实现，确保同一套计算逻辑
  - 在线推理（Java 特征服务）直接调用本地 `feature-engine` Java API
  - 特征计算逻辑：归一化（min-max / z-score 的边界值处理）、缺失值填充（默认值 / 中位数 / 0）、类别特征编码（哈希函数、空值编码）
- **`feature-definition.yml` 强化**：每个特征必须明确声明：
  - 计算逻辑（伪代码）
  - 归一化公式与边界值
  - 缺失值处理策略
  - 默认值
  - 数据类型、取值范围
  - 作为离线和在线实现的唯一权威依据
- **每日特征一致性校验任务**（Spark，每日 02:00 训练样本构建后执行）：
  - 随机抽取 1000 条样本
  - 用在线特征服务（Java）重新计算特征
  - 与离线训练样本的特征逐字段对比
  - 偏差阈值：连续特征最大绝对误差 ≤ 1e-6，类别特征一致性 100%
  - 偏差超阈值则告警并**阻断模型发布**

### 2.4 服务层

**职责**：提供原子化的领域服务，被应用层编排调用，服务之间低耦合、高内聚。

#### 2.4.1 召回服务（RecallService）

| 召回通道 | 实现方式 | 数据来源 | 候选数量 |
|---------|---------|---------|---------|
| 协同过滤召回（ItemCF） | 基于物品相似度矩阵，取用户历史交互物品的 Top-N 相似物品 | Redis（相似度矩阵缓存）/ MySQL（离线计算结果） | ≥ 100 |
| 内容标签召回 | 基于用户偏好标签，匹配物品标签，按标签权重排序 | MongoDB（用户画像标签）+ ES（物品标签索引） | ≥ 100 |
| 用户画像召回 | 基于用户长期画像的类目偏好，召回对应类目高热度物品 | MongoDB（长期画像）+ MySQL（物品热度） | ≥ 100 |
| 热门趋势召回 | 全局/类目热门物品，按近 24 小时点击量排序 | Redis（实时热门计数）/ MySQL（离线热度） | ≥ 100 |
| ES 检索召回 | 文本关键词检索 + kNN 语义检索（搜索场景） | ES `item_index`（含 IK 分词 + Embedding） | ≥ 100 |

**召回合并策略**：
- 多路召回结果合并后按 `itemId` 去重。
- 每路召回结果携带 `recallChannel` 标记，用于后续分析与归因。
- **合并后截断至 200~300**（修复 P1-06，原 200~500 导致 DeepFM batch 过大），传入排序层。

#### 2.4.2 排序服务（RankService）

| 阶段 | 模型 | 输入 | 输出 | 说明 |
|-----|------|------|------|------|
| 粗排（可选） | 轻量逻辑回归 / 规则 | 召回候选 + 基础特征 | Top-N 筛选 | 单机 1000 QPS 下可省略粗排，直接精排 |
| 精排 | XGBoost 或 DeepFM | 候选物品 + 用户/物品/上下文 30+ 维特征 | 预测 CTR/CVR 分数 | 模型可配置切换，A/B 实验对比 |
| 重排 | 规则 + 多样性算法 | 精排分数 + 物品类目 | 最终排序结果 | 类目打散、业务规则过滤、长尾物品加权 |

**模型调用流程**（修复 P1-06）：
1. 排序服务从特征服务获取候选物品的特征向量。
2. 批量组装为 `PredictRequest`（batch_size = 候选数量，已收紧至 200~300）。
3. **三级降级链路**：
   - **一级**：根据 A/B 配置调用主模型（如 DeepFM），gRPC 超时 **80ms**（原 50ms）
   - **二级**：DeepFM 超时/失败 → 同步调用 XGBoost 模型（同一推理服务内，gRPC 超时 20ms）
   - **三级**：XGBoost 也失败 → 降级为规则排序（物品热度分 + 随机扰动），返回错误码 `400002`
4. 收到 `PredictResponse` 后，按预测分数降序排列。
5. 执行重排规则，返回最终 Top-K（默认 20）。

**精排阶段延迟预算**（修复 P1-06）：
- DeepFM 推理（CPU，batch=300）≈ 20~40ms
- gRPC 序列化/网络（本地回环）≈ 2~5ms
- DeepFM 超时阈值：80ms（含网络）
- XGBoost 降级调用：5ms 内
- **精排阶段总预算 < 50ms**（原 30ms），总延迟预算调整为 P50 < 100ms、P99 < 200ms（仍满足 PERF-02/PERF-03）

#### 2.4.3 特征服务（FeatureService）

**职责**：统一管理特征定义、特征组装、特征缓存，**确保离线/在线特征一致性**（修复 P1-03）。

| 特征类别 | 来源 | 更新频率 | 缓存策略 |
|---------|------|---------|---------|
| 用户静态特征 | MySQL（用户基础信息） | 不变 | Redis 缓存，TTL 1 小时 |
| 用户长期画像特征 | MongoDB（Spark T+1 计算） | T+1 | Redis `user:profile:long` 缓存，TTL 300s |
| 用户实时短期特征 | MongoDB（Flink 秒级更新） | 秒级 | Redis `user:profile:short` 缓存，TTL 5s（不主动失效） |
| 物品静态特征 | MySQL（物品元数据） | 低频变更 | Redis 缓存，TTL 10 分钟 |
| 物品统计特征 | Redis（Flink 实时计数）/ Spark 离线 | 秒级 / T+1 | 直接读 Redis |
| 物品 Embedding | ES（离线批量生成） | T+1 | 直接读 ES |
| 上下文特征 | 请求参数（时间、设备、场景） | 每次请求 | 不缓存 |

**特征定义配置化**：所有特征在 `feature-definition.yml` 中定义，每个特征必须明确声明：
- 特征名、类型（int/float/category/vector）
- 来源、更新频率
- 默认值、归一化公式与边界值
- 缺失值处理策略
- 取值范围
- 计算逻辑伪代码

**特征一致性保障**（修复 P1-03）：
- 特征计算逻辑封装为独立 `feature-engine` 模块，提供 Java 和 Python 双语言实现
- 离线训练通过 Py4J 网关调用 Java 实现，在线推理直接调用 Java API，确保同一套计算逻辑
- **每日训练样本构建后执行特征一致性校验任务**：
  - 随机抽取 1000 条样本
  - 用在线特征服务重新计算特征
  - 与离线训练样本的特征逐字段对比
  - 连续特征最大绝对误差 ≤ 1e-6，类别特征一致性 100%
  - 偏差超阈值则告警并阻断模型发布

#### 2.4.4 用户画像服务（UserProfileService）

**职责**：用户画像的读写、实时更新、长期画像与短期画像融合。

- **读路径**（修复 P1-01）：
  - 分别读取 `user:profile:long:{userId}`（TTL 300s）和 `user:profile:short:{userId}`（TTL 5s）两个 Redis Key
  - 任一未命中查 MongoDB 对应字段
  - **应用层加权融合**：短期画像权重 0.6 / 长期画像权重 0.4（可配置）
- **写路径（实时，Flink）**（修复 P1-01 / P1-08 / P2-05）：
  - Flink 计算后使用 `$set` 操作符**仅更新 `shortTerm` 字段**，**不调用 Redis DEL**
  - 短期画像靠 Redis 5 秒 TTL 自然过期，MongoDB 字段级 `$set` 保证不覆盖 longTerm
- **写路径（离线，Spark）**：
  - Spark 批量使用 `$set` **仅更新 `longTerm` 字段**，禁止全文档替换
  - 离线任务完成后主动失效 `user:profile:long:{userId}` 缓存

#### 2.4.5 模型推理代理（ModelInferenceProxy）

**职责**：封装 gRPC 调用细节，管理模型版本路由、超时、降级、批量优化。

- **模型版本路由**：根据配置（`model.rank.active=xgboost_v2` 或 `deepfm_v1`）选择模型，支持灰度切换。
- **批量优化**：同一请求内多个候选物品合并为一次 gRPC 调用。
- **请求入口快照**（修复 P2-06）：
  - 请求进入推理队列时**快照当前活跃模型引用**
  - 排队和推理过程中始终使用该快照，不受热加载影响
  - 同一批候选物品保证使用同一个模型
- **三级降级策略**（修复 P1-06）：DeepFM 超时 → XGBoost（同步调用，<5ms）→ 规则排序
- **预测缓存修正**（修复 P1-06）：
  - 缓存 Key 改为 `model:predict:{modelVersion}:{featureHash}`
  - 仅对实时特征变化不敏感的物品静态特征部分单独缓存
  - 实时特征场景下缓存价值有限，TTL 缩短至 5 秒
- **Embedding 在线调用**（修复 P1-05）：
  - 搜索场景调用模型推理服务 `/embed` HTTP 接口
  - 关键词向量化，超时 50ms

### 2.5 计算层

#### 2.5.1 实时计算（Flink）

**拓扑结构**（修复 P1-02 / P1-08）：
```
Kafka(behavior_topic) → Flink Source (事件时间 + Watermark 5s 乱序)
    → BehaviorParseFunction (解析/过滤)
    → KeyedStream (keyBy userId)
    → RealtimeFeatureAggregator (1min 滚动窗口 + AggregateFunction 增量聚合)
        │  仅维护 clickCount/viewCount/favoriteCount 三个 long 计数器
        │  不存储原始事件，状态体积稳定
        ↓
        ┌────────────────────┬────────────────────────┬────────────────────┐
        │ 分支1: Redis Sink  │ 分支2: MongoDB Sink     │ 分支3: MongoDB Sink│
        │ 实时行为计数        │ 短期画像更新            │ 行为明细落库       │
        │ ZADD (幂等)        │ $set shortTerm 字段     │ insertOne +        │
        │ member=itemId+ts   │ 字段级原子操作          │ eventId 唯一键     │
        │ score=timestamp    │ 不调用 Redis DEL        │ ordered=false      │
        └────────────────────┴────────────────────────┴────────────────────┘
```

**关键算子**（修复 P1-02）：
- `BehaviorParseFunction`：解析 JSON 行为事件，校验字段，过滤无效数据。
- `RealtimeFeatureAggregator`：**`KeyedProcessFunction` 改为 `KeyedWindow + AggregateFunction`**：
  - 窗口类型：1 分钟滚动窗口（`TumblingEventTimeWindows.of(Time.minutes(1))`）
  - 增量聚合：`AggregateFunction` 实现仅维护 3 个 long 计数器（clickCount/viewCount/favoriteCount）
  - 不存储原始事件，状态体积恒定
  - 1 小时聚合结果由 60 个 1 分钟窗口在应用层累加得到
  - 触发器：事件时间 Watermark 触发
- `ShortTermProfileUpdater`：`SinkFunction`，使用 `$set shortTerm` 字段级更新 MongoDB（修复 P2-05）。
- `BehaviorDetailSink`：`SinkFunction`，批量写入 MongoDB `user_behavior`（每 100 条或 1 秒刷一次），使用 `eventId` 幂等键（修复 P1-08）。

**Checkpoint 配置**：间隔 30 秒，超时 60 秒，最小间隔 10 秒，失败容忍 3 次。

#### 2.5.2 离线计算（Spark）

**任务列表**（含新增的 Embedding 生成与特征一致性校验任务）：

| 任务 | 调度周期 | 输入 | 输出 | 说明 |
|-----|---------|------|------|------|
| 物品热度统计 | 每日 00:30 | MongoDB 行为明细（近 24 小时） | MySQL `item_hotness` + Redis | 按点击量排序，用于热门召回 |

## 三、核心业务链路

### 3.1 推荐请求主链路（端到端）

**触发**：客户端调用 `GET /api/v1/recommend`

```
客户端 → Nginx(可选) → Spring MVC Controller → TraceIdFilter → 鉴权拦截器
    → Resilience4j 限流
    → RecommendationFacade.recommend(scene, userId, context)
        │
        ├─ 1. A/B 分流：AbExperimentService.assign(userId, experimentId)
        │     ├─ 查实验配置（MySQL experiment 表 + configVersion，缓存到 Redis 5 分钟）
        │     ├─ 查 Redis 缓存 ab:user:{userId}:{experimentId}:{configVersion}
        │     ├─ 未命中 → MurmurHash3(userId + ":" + experimentId) % 100（修复 P2-01）
        │     └─ 返回实验组标识（如 "xgboost_v2" / "deepfm_v1" / "control"）
        │
        ├─ 2. 缓存检查：RedisService.get("rec:result:{scene}:{userId}:{abGroup}:{modelVersion}")
        │     ├─ 命中 → 直接返回（记录缓存命中指标）
        │     └─ 未命中 → 继续后续流程
        │
        ├─ 3. 场景策略选择：SceneStrategyFactory.getStrategy(scene)
        │     ├─ home → HomeStrategy
        │     ├─ guess → GuessStrategy
        │     ├─ related → RelatedStrategy（需 itemId 参数）
        │     └─ search → SearchStrategy（需 keyword 参数，含语义检索）
        │
        ├─ 4. 多路召回：RecallService.recall(userId, itemId, scene, channels)
        │     ├─ 4.1 ItemCF 召回：ItemCFRecaller.recall(userId)
        │     ├─ 4.2 内容标签召回：TagRecaller.recall(userId)
        │     ├─ 4.3 用户画像召回：ProfileRecaller.recall(userId)
        │     ├─ 4.4 热门趋势召回：HotRecaller.recall(userId)
        │     ├─ 4.5 ES 检索召回（仅搜索/相关场景）：ESRecaller.recall(keyword/itemId)
        │     └─ 4.6 合并去重+截断：RecallMerger.merge(results)
        │           ├─ 按 itemId 去重，保留最高分与召回通道标记
        │           └─ 输出候选集（200~300 个物品，修复 P1-06）
        │
        ├─ 5. 特征组装：FeatureService.assemble(userId, candidateItems, context)
        │     ├─ 5.1 批量查用户特征（长期+短期，分别从 Redis 两个 Key 读取）
        │     ├─ 5.2 批量查物品特征（静态+统计+Embedding，Redis/MySQL/ES）
        │     ├─ 5.3 组装上下文特征（时间、设备、场景）
        │     └─ 5.4 调用 feature-engine 模块归一化，输出特征向量列表
        │
        ├─ 6. 精排：RankService.rank(candidates, features, modelVersion)
        │     ├─ 6.1 批量组装 PredictRequest（特征向量矩阵，batch 200~300）
        │     ├─ 6.2 三级降级链路：
        │     │     ├─ 一级：gRPC 调用主模型（DeepFM，超时 80ms）
        │     │     ├─ 二级：DeepFM 超时 → 同步调用 XGBoost（超时 20ms）
        │     │     └─ 三级：XGBoost 失败 → 规则排序（热度分），返回 400002
        │     ├─ 6.3 入口快照模型引用（修复 P2-06），保证同批候选使用同一模型
        │     ├─ 6.4 按预测分数降序排列
        │     └─ 6.5 重排：ReRanker.rerank(rankedItems)
        │           ├─ 类目打散（相邻物品不同类目，最多尝试 3 次）
        │           ├─ 长尾物品加权（热度后 50% 物品分数 × 1.1，满足 ALG-06）
        │           ├─ 业务规则过滤（已购买/已曝光过滤）
        │           └─ 取 Top-20
        │
        ├─ 7. 缓存写入：RedisService.set(...)
        │     TTL 根据用户活跃度分层（高频 10s / 普通 60s / 兜底 120s）
        │
        ├─ 8. 曝光埋点：异步发送曝光事件到 Kafka（behavior_topic, type=impression）
        │     含 acks=all + 幂等生产者 + 本地缓冲兜底
        │
        └─ 9. 返回统一响应格式（含 traceId、abGroup、modelVersion、推荐列表）
```

**各节点输入/处理/输出明细**：

| 节点 | 输入 | 处理逻辑 | 输出 | 性能预算 |
|-----|------|---------|------|---------|
| 鉴权拦截器 | HTTP Header X-API-Key | 比对配置中的密钥 | 通过/拒绝 | < 1ms |
| A/B 分流 | userId, experimentId, configVersion | Redis 查缓存 → MurmurHash3 → 写缓存 | abGroup 标识 | < 2ms |
| 缓存检查 | scene, userId, abGroup, modelVersion | Redis GET | 推荐结果 / null | < 2ms |
| 多路召回 | userId, scene | 并行执行 4 路召回（CompletableFuture），合并去重+截断 | 候选物品列表（200~300） | < 30ms |
| 特征组装 | userId, candidates, context | 批量查询用户/物品特征，归一化 | 特征向量列表 | < 15ms |
| 精排推理 | 特征向量矩阵 | gRPC 批量推理（ONNX Runtime）+ 三级降级 | 预测分数列表 | < 50ms（含降级） |
| 重排 | 排序结果 | 类目打散 + 长尾加权 + 过滤 | Top-20 最终列表 | < 3ms |
| 缓存写入 | 推荐结果 | Redis SETEX（分层 TTL） | — | 异步，不阻塞 |
| 曝光埋点 | 曝光事件 | Kafka 异步发送（acks=all + 本地缓冲） | — | 异步，不阻塞 |

**总延迟预算**（修复 P1-06 后）：
- 缓存未命中时 P50 < 100ms（原 80ms），P99 < 200ms（满足 PERF-02/PERF-03）
- 缓存命中时 < 5ms

### 3.2 实时行为采集与特征更新链路

**触发**：客户端调用 `POST /api/v1/behavior` 上报行为事件

```
客户端 → BehaviorCollectorController → 参数校验
    → KafkaProducerService.send("behavior_topic", behaviorEvent)
        │  (异步发送，acks=all，enable.idempotence=true，立即返回成功)
        │  失败回调 → LocalFileBuffer.write(buffer/behavior/{date}.log)
        │  后台线程每 10s 检查 Kafka 可用性，恢复后批量重放
        ↓
Kafka behavior_topic (3 partitions, key=userId)
        ↓
Flink Source (Kafka Consumer, group.id=flink-realtime-feature)
        ↓
WatermarkStrategy.BoundedOutOfOrderness(Duration.ofSeconds(5))  // 事件时间 + 乱序容忍
        ↓
BehaviorParseFunction (Map)
    - 解析 JSON，校验必填字段（userId, itemId, actionType, eventTime, scene）
    - 过滤无效数据（actionType 不在枚举内 / eventTime 偏差 > 1 小时）
    - 生成 eventId = MurmurHash3(userId + itemId + actionType + eventTime)
        ↓
KeyedStream (keyBy userId)
        ↓
RealtimeFeatureAggregator (1min 滚动窗口 + AggregateFunction 增量聚合)
    - 窗口类型：TumblingEventTimeWindows.of(Time.minutes(1))
    - AggregateFunction 实现：仅维护 clickCount/viewCount/favoriteCount 三个 long 计数器
    - 不存储原始事件，状态体积恒定
    - 1h 聚合 = 60 个 1min 窗口在应用层累加
        ↓
    ┌─────────────────┬──────────────────────┬──────────────────────┐
    │ 分支1: Redis Sink│ 分支2: MongoDB Sink   │ 分支3: MongoDB Sink   │
    │ 实时行为计数      │ 短期画像更新          │ 行为明细落库          │
    │ ZADD (幂等)      │ $set shortTerm 字段  │ insertOne +          │
    │ user:action:    │ 字段级原子操作        │ eventId 唯一键       │
    │ {userId}:{type} │ 不调用 Redis DEL      │ ordered=false        │
    │ member=itemId+ts│ 靠 5s TTL 自然过期    │ 重复键异常捕获        │
    │ score=timestamp │                      │                      │
    └─────────────────┴──────────────────────┴──────────────────────┘
```

**端到端延迟计算**（满足 PERF-05 < 5 秒，修复 P1-02）：
- 行为上报 → Kafka：< 100ms（网络 + 生产）
- Kafka → Flink 消费：< 500ms（轮询间隔 100ms + 处理）
- Flink 1min 窗口触发：≤ 1 秒（增量聚合，触发后即写入，无需遍历）
- Flink → Redis/MongoDB 写入：< 200ms
- **总延迟 P99 < 2 秒**（原报告估算 < 3 秒，现采用增量聚合后进一步优化）

### 3.3 离线画像与相似度计算链路

**触发**：每日定时调度（单机使用 Spring `@Scheduled` 或系统 cron）

**含失败重试与告警机制**（修复 P2-08）：

```
每日 00:30 ── 物品热度统计任务 (Spark)
    ├─ 读取 MongoDB user_behavior（近 24 小时 click 事件）
    ├─ 按 itemId 分组计数，计算热度分（点击量 × 0.7 + 收藏量 × 0.3）
    ├─ 写入 MySQL item_hotness 表（覆盖更新）
    ├─ 同步 Top-1000 热门物品到 Redis
    └─ 校验输出：热度榜物品数 ≥ 1000，否则标记任务失败

每日 01:00 ── 用户长期画像任务 (Spark)
    ├─ 读取 MongoDB user_behavior（近 30 天全量行为）
    ├─ 按 userId 聚合：
    │   ├─ 类目偏好分布（各类目点击占比，Top-10 类目）
    │   ├─ 标签权重（TF-IDF 计算用户偏好标签，Top-20 标签）
    │   ├─ 活跃度（近 7 天 / 30 天行为次数）
    │   ├─ 活跃时段（24 小时分布）
    │   └─ 价格偏好（交互物品价格分位数）
    ├─ 组装为 20+ 维长期画像文档
    ├─ Bulk Write 到 MongoDB user_profile.longTerm（$set 字段级 upsert）
    └─ 主动失效 Redis user:profile:long:{userId}（按变更用户批量 DEL）

每日 01:30 ── 物品相似度矩阵任务 (Spark)
    ├─ 读取 MongoDB user_behavior（近 30 天 click/favorite 事件）
    ├─ 构建用户-物品交互矩阵
    ├─ 计算物品共现矩阵：itemA × itemB 共同交互用户数
    ├─ 余弦相似度：sim(A,B) = co(A,B) / sqrt(|A| × |B|)
    ├─ 每个物品取 Top-50 相似物品（相似度 > 0.01 阈值）
    ├─ 写入 MySQL item_similarity 表
    ├─ 同步到 Redis（ZSET item:sim:{itemId}）
    └─ 校验：相似度条目 ≥ 100,000，否则标记任务失败（满足 DATA-03）

每日 02:00 ── 训练样本构建任务 (Spark)
    ├─ 读取行为明细 + 用户画像 + 物品元数据
    ├─ 正样本：click/favorite/conversion 事件
    ├─ 负样本：曝光未点击（负采样比例 1:5）
    ├─ 特征工程：调用 feature-engine 模块（修复 P1-03）
    ├─ 按 8:1:1 划分训练/验证/测试集（按 userId 哈希划分，防泄露）
    └─ 输出 Parquet 文件到 /data/training_samples/{date}/

每日 02:30 ── 特征一致性校验任务 (Spark，新增，修复 P1-03)
    ├─ 随机抽取 1000 条训练样本
    ├─ 调用在线特征服务（Java）重新计算特征
    ├─ 与离线训练样本特征逐字段对比
    │   ├─ 连续特征：最大绝对误差 ≤ 1e-6
    │   └─ 类别特征：一致性 100%
    ├─ 偏差超阈值 → 写入 MySQL feature_consistency_log，状态=FAILED，阻断模型发布
    └─ 偏差正常 → 状态=PASSED，允许模型训练流程

每日 02:30 ── 物品 Embedding 生成任务 (Python，新增，修复 P1-05)
    ├─ 读取物品元数据（名称+描述+标签）
    ├─ 调用 text2vec-base-chinese 生成 768 维向量
    ├─ PCA 降维至 128 维
    ├─ 增量写入 ES item_index.embedding 字段
    └─ 仅更新当日变更的物品（增量更新，减少计算量）
```

**任务依赖与失败重试**（修复 P2-08）：
- DAG 调度：热度统计 → 长期画像 → 相似度矩阵 → 训练样本 → 一致性校验 → Embedding 生成
- 单任务失败：自动重试 2 次，间隔 5 分钟
- 重试仍失败：发送 Webhook 告警（钉钉/飞书），终止 DAG
- 手动补跑：`./offline-scheduler.sh --rerun {taskName}`
- 输出数据量校验：每个任务完成后校验输出（如相似度矩阵 ≥ 100,000 条），不达标则标记失败

**完成时间目标**：全部任务在每日 03:00 前完成（原 02:00 调整为 03:00，因新增特征一致性校验和 Embedding 生成任务），相似度矩阵任务为最长任务，预计 30~60 分钟。

### 3.4 模型训练与发布链路

**触发**：训练样本就绪且特征一致性校验通过后手动触发或定时触发（每日 03:00）

```
训练样本 Parquet + 特征一致性校验通过 → train_pipeline.py
    │
    ├─ 1. 数据加载：加载训练/验证/测试集
    ├─ 2. 特征校验：校验特征维度与 feature-definition.yml 一致
    │
    ├─ 3. XGBoost 训练分支
    │   ├─ 初始化 XGBClassifier（GPU/CPU 自动检测）
    │   ├─ 训练（early_stopping on validation set）
    │   ├─ 测试集评估：AUC, LogLoss, PR-AUC
    │   ├─ 特征重要性输出（SHAP / gain）
    │   └─ 导出 ONNX（opset=15）→ xgboost_v{n}_{date}.onnx
    │
    ├─ 4. DeepFM 训练分支
    │   ├─ 构建 DeepFM 模型（FM + DNN）
    │   ├─ 训练（AdamW, EarlyStopping）
    │   ├─ 测试集评估：AUC, LogLoss, PR-AUC
    │   └─ 导出 ONNX（opset=17）→ deepfm_v{n}_{date}.onnx
    │
    ├─ 5. 模型质量门禁
    │   ├─ XGBoost AUC ≥ 0.78？不通过则不发布，告警
    │   ├─ DeepFM AUC ≥ 0.80？不通过则不发布，告警
    │   └─ 特征一致性校验状态=PASSED？不通过则阻断发布
    │
    ├─ 6. 模型发布
    │   ├─ 复制 ONNX 文件到模型服务模型目录（/models/active/）
    │   ├─ 更新 MySQL model_version 表（版本号、路径、指标、状态=active）
    │   ├─ 发送 Kafka 消息到 model_update_topic
    │   └─ 模型推理服务收到消息后热加载新模型（入口快照机制）
    │
    └─ 7. 生成训练报告 metrics.json（AUC、LogLoss、训练耗时、特征一致性报告、特征重要性 Top-20）
```

**模型热加载机制**（修复 P2-06）：
- 模型推理服务监听 Kafka `model_update_topic`。
- 收到消息后，从模型目录加载新 ONNX 文件到内存（`InferenceSession`）。
- 加载完成后原子切换活跃模型引用（`AtomicReference`）。
- **请求入口快照机制**：
  - 请求进入推理队列时快照当前活跃模型引用
  - 排队和推理过程中始终使用该快照
  - 同一批候选物品保证使用同一个模型
- 旧模型保留 10 分钟用于回滚，之后卸载。

### 3.5 A/B 实验分流链路

**触发**：每次推荐请求时调用

```
RecommendationFacade → AbExperimentService.assign(userId, experimentId)
    │
    ├─ 1. 查实验配置（MySQL experiment 表 + configVersion，缓存到 Redis 5 分钟）
    │     ├─ 实验状态：running / paused / ended
    │     ├─ 分流比例：如实验组 50% / 对照组 50%（粒度 1%）
    │     ├─ 实验组配置：模型版本、召回通道配置等
    │     └─ configVersion：实验配置每次更新自增
    │
    ├─ 2. 查用户分流缓存（Redis: ab:user:{userId}:{experimentId}:{configVersion}）
    │     ├─ configVersion 不匹配 → 视为未命中，重新分流
    │     ├─ 命中 → 直接返回已分配的组
    │     └─ 未命中 → 继续分流
    │
    ├─ 3. 哈希分流（修复 P2-01）：MurmurHash3(userId + ":" + experimentId) % 100
    │     ├─ 0~49 → 实验组 A（如 xgboost_v2）
    │     └─ 50~99 → 对照组 B（如 deepfm_v1 / control）
    │
    ├─ 4. 写入 Redis 缓存（Key 含 configVersion，TTL = 实验结束时间）
    │
    └─ 5. 返回 abGroup + 实验参数（模型版本、召回配置等）
```

**实验配置更新机制**（修复 P2-04）：
- 配置更新接口（`PUT /admin/ab/experiments/{experimentId}`）执行：
  1. 更新 MySQL experiment 表，`configVersion` 自增
  2. 失效 Redis `ab:experiment:{experimentId}:config` 配置缓存
  3. 旧 `ab:user:{userId}:{experimentId}:{oldVersion}` 缓存自然过期（最多 5 分钟）
  4. 新请求以新 configVersion 重新分流

**实验指标统计**：
- 曝光/点击/转化事件携带 `abGroup` 字段写入 Kafka。
- Flink 实时聚合各实验组的曝光数、点击数、转化数（1 分钟滚动窗口）。
- 实验报告接口（`GET /admin/ab/{experimentId}/report`）查询聚合结果，计算 CTR、CVR、浏览时长，并进行统计显著性检验（t 检验 / 卡方检验，P < 0.05 为显著）。

### 3.6 搜索召回链路（搜索场景，修复 P1-05）

**触发**：客户端调用 `GET /api/v1/search?keyword=xxx`

```
SearchController → RecommendationFacade.recommend(scene="search", keyword)
    │
    ├─ 1. ES 文本检索：ESRecaller.textSearch(keyword)
    │     ├─ multi_match query（name, description, tags 字段，IK 分词）
    │     ├─ BM25 相似度打分
    │     └─ 取 Top-100
    │
    ├─ 2. ES 语义检索：ESRecaller.semanticSearch(keyword)
    │     ├─ 关键词向量化：HTTP 调用模型推理服务 /embed 接口（端口 8083，超时 50ms）
    │     │   ├─ 调用 text2vec-base-chinese 生成 768 维 → PCA 128 维
    │     │   └─ 失败 → 跳过语义检索分支，仅返回文本检索结果
    │     ├─ knn 查询（cosine 相似度，HNSW 索引，k=100，num_candidates=200）
    │     └─ 取 Top-100
    │
    ├─ 3. 文本与语义结果加权融合（RRF 倒数排名融合）
    │
    ├─ 4. 后续流程同推荐主链路（特征组装 → 精排 → 重排 → 返回）
    │
    └─ 响应时间目标 < 50ms（ES 检索部分，满足 CORE-02）
```

**Embedding 一致性保证**：
- 物品 embedding（离线生成）与查询 embedding（在线生成）使用**同一模型 text2vec-base-chinese**
- 同一 PCA 降维矩阵（离线训练后保存，在线推理时加载）
- 保证物品与查询 embedding 处于同一向量空间，cosine 相似度有意义

- 物品与查询使用同一模型与同一 PCA 矩阵，保证同向量空间

**检索方式**：
- 文本检索：`multi_match` query，字段 `name^3, description, tags^2`，BM25 打分，IK 分词。
- 标签检索：`terms` query 匹配 `tags` 字段，按匹配标签数打分。
- 语义检索：`knn` 查询，`field=embedding`，`k=100`，`num_candidates=200`。
- 混合检索：文本 + kNN 通过 `rank` 融合（RRF）。

### 4.5 Kafka Topic 设计

| Topic 名称 | 分区数 | 副本数 | 保留时间 | 压缩 | 用途 |
|-----------|-------|-------|---------|------|------|
| `behavior_topic` | 3 | 1 | 7 天 | lz4 | 用户行为事件（点击/浏览/收藏/曝光/转化） |
| `realtime_feature_topic` | 3 | 1 | 1 天 | lz4 | Flink 计算后的实时特征（供下游消费） |
| `model_update_topic` | 1 | 1 | 7 天 | lz4 | 模型更新通知（模型服务监听热加载） |
| `ab_event_topic` | 3 | 1 | 7 天 | lz4 | A/B 实验事件（用于实验指标统计） |
| **`feature_consistency_topic`** | 1 | 1 | 7 天 | lz4 | **特征一致性校验任务结果通知**（修复 P1-03） |

**消息 Key**：`behavior_topic` 和 `realtime_feature_topic` 使用 `userId` 作为 Key，保证同一用户行为有序。

**消息格式**：JSON（value.serializer=StringSerializer），行为事件格式见 3.2 节（含 eventId）。

### 4.6 表关联关系

```
user(user_id) ──1:N──> user_behavior(userId)
user(user_id) ──1:1──> user_profile(userId)

item(item_id) ──1:N──> user_behavior(itemId)
item(item_id) ──1:1──> item_hotness(item_id)
item(item_id) ──1:N──> item_similarity(item_id → similar_item_id)
item(item_id) ──1:1──> item_index(itemId, ES, 含 Embedding)

experiment(experiment_id, config_version) ──1:N──> ab_event_topic(experimentId)
experiment.groups_config.modelVersion ──引用──> model_version(version)
model_version(version) ──1:N──> feature_consistency_log(check_date)
```

**关联查询策略**：
- 推荐链路中避免 MySQL JOIN，使用应用层批量查询 + 内存组装（性能优先）。
- 用户画像与行为明细通过 `userId` 关联，在 MongoDB 中分别存储，应用层融合。
- 物品相似度通过 `item_id` 关联，Redis ZSET 缓存热点数据。

### 6.3 高可用方案

**单机环境高可用策略**（含本地缓冲机制，修复 P1-10）：

| 故障场景 | 检测方式 | 降级策略 | 恢复方式 |
|---------|---------|---------|---------|
| Redis 不可用 | 连接池健康检查 + 调用异常计数 | 推荐结果绕过缓存直接计算；用户画像直接查 MongoDB；物品信息直接查 MySQL；实时计数降级为内存计数器 | 重启 Redis，缓存自动回写 |
| MongoDB 不可用 | 健康检查 + 调用异常 | 用户画像降级为默认画像；行为明细写入失败时缓冲到 Kafka（增加 retention） | 重启 MongoDB，Flink 从 Checkpoint 恢复 |
| MySQL 不可用 | HikariCP 连接检查 | 物品元数据走 Redis 缓存；实验配置走 Redis 缓存 | 重启 MySQL，缓存自动回写 |
| Elasticsearch 不可用 | 健康检查 | ES 召回通道关闭，剩余 3 路召回保证可用性；搜索场景返回 `500002` | 重启 ES，重新索引物品数据 |
| **Kafka 不可用** | **生产者回调异常** | **行为采集接口返回成功但事件写入本地文件缓冲（`buffer/behavior/{date}.log`），后台线程每 10s 检查 Kafka 可用性，恢复后批量重放** | **重启 Kafka，重放缓冲文件**（修复 P1-10） |
| 模型推理服务不可用 | gRPC 健康检查 + 调用超时 | **三级降级：DeepFM → XGBoost（同服务内同步调用，<5ms）→ 规则排序** | 重启模型服务，热加载模型后自动恢复 |
| Embedding 服务不可用 | HTTP 健康检查 | 语义检索分支跳过，仅返回文本检索结果（RRF 融合降级） | 重启模型推理服务 |
| Flink 任务失败 | Checkpoint 超时 / 进程退出 | 实时特征停止更新，使用最近一次画像 | 从最近 Checkpoint 重启 Flink 任务 |

**推荐接口可用性目标**：即使任一依赖组件故障，推荐接口仍能返回结果（可能降级），不返回 5xx 错误。核心降级链路：缓存 → 直接计算 → DeepFM 推理 → XGBoost 推理 → 规则排序 → 热门兜底。

### 6.4 弹性扩缩容策略

**单机环境**：无弹性扩缩容（基线约束），但架构设计支持集群化扩展。

**集群化扩展策略**（迁移后适用）：

| 组件 | 扩展方式 | 扩展依据 | 配置变更 |
|-----|---------|---------|---------|
| 推荐服务 | 无状态水平扩展，前置 Nginx/LB 负载均衡 | CPU > 70% 持续 3 分钟 → 扩容 | 仅修改实例数，代码零修改 |
| Redis | 集群模式（Redis Cluster），16384 槽分片 | 内存 > 80% → 增加分片 | 修改 `spring.redis.cluster.nodes` |
| MongoDB | 副本集（高可用）+ 分片集群（按 userId 哈希分片） | 数据量 > 单节点 500GB → 分片 | 修改连接串为副本集/分片集群地址 |
| MySQL | 主从复制（读写分离）+ 分库分表（按 userId 取模） | 单表 > 1000 万行 → 分表 | 引入 ShardingSphere |
| Elasticsearch | 增加节点，索引分片数调整 | 搜索延迟 > 100ms → 增加节点/分片 | 修改 `number_of_replicas` 和节点列表 |
| Kafka | 增加 Broker，分区数扩容 | 消息积压 > 10 万条 → 增加分区 | 修改 `bootstrap.servers` 和分区数 |
| Flink | 增加 TaskManager，调整并行度 | 反压持续 > 1 分钟 → 增加并行度 | 修改 `parallelism.default` |
| 模型推理服务 | 无状态水平扩展，gRPC 负载均衡 | 推理延迟 P99 > 50ms → 扩容 | 修改 gRPC 服务发现地址列表 |

**线性扩展系数**：设计目标 0.8（即 N 节点 QPS = 单机 QPS × N × 0.8），125 节点可达 100,000 QPS（满足 PERF-04）。

### 6.5 缓存命中率优化方案（修复 P1-09）

**问题分析**：
- 原 TTL 60 秒 + 均匀用户分布 → 缓存命中率趋近于 0
- PERF-07 目标 ≥ 60% 难以达成

**优化策略**：

1. **压测用户访问模型**：使用 **Zipf 分布**（20% 用户贡献 80% 请求），固定 2000 个高频用户反复请求，模拟真实场景中的热点用户效应
2. **分层 TTL 策略**：
   - 高频用户（近 5 分钟访问次数 > 10）：TTL 10 秒（修复 P2-03，对实时特征友好）
   - 普通用户：TTL 60 秒
   - 兜底（无行为数据）：TTL 120 秒
3. **热点预缓存机制**：
   - 后台线程异步预刷新高频用户的推荐结果
   - 缓存过期前 10 秒主动重新计算并更新缓存
   - 用户请求始终命中缓存
4. **行为触发失效**：高活跃用户行为上报时主动失效该用户的推荐结果缓存（`DEL rec:result:{scene}:{userId}:{abGroup}:{modelVersion}`），保证实时性
5. **命中率测算**：
   - 基于 Zipf 分布 + 2000 高频用户 + 1000 QPS + 平均访问间隔 2 秒
   - 理论命中率：高频用户 80% 命中 + 普通用户 20% 命中 = 综合命中率 65~70%
   - 满足 PERF-07（≥ 60%）

### 6.6 服务启停编排（新增，修复 P0-01）

**离线窗口（00:30 - 03:00）服务编排**：

```bash
# offline-window.sh - 离线窗口服务启停编排脚本

# 00:25 - 暂停 Flink TaskManager（释放约 0.5 GB）
flink.sh stop-taskmanager

# 00:25 - 暂停模型推理服务（释放约 0.5 GB）

flink.sh start-taskmanager
```

**暂停顺序**：Flink TaskManager → 模型推理服务 → 启动 Spark
**恢复顺序**：Spark 完成 → 模型推理服务 → Flink TaskManager

**安全检查**：
- 启动 Spark 前检查可用内存 ≥ 4 GB
- 离线任务全部完成后才恢复服务
- 异常情况（如 Spark 任务失败）触发告警，人工介入恢复服务

### 6.8 集群化迁移路径

**核心原则**：代码零修改，仅修改配置文件（满足基线架构可扩展目标）。

**迁移步骤**：

1. **中间件集群化**：
   - MySQL：单节点 → 主从复制 → 分库分表（ShardingSphere）
   - Redis：单节点 → Redis Cluster（至少 3 主 3 从）
   - MongoDB：单节点 → 副本集（3 节点）→ 分片集群
   - Kafka：单节点 KRaft → 多 Broker KRaft 集群（至少 3 节点）
   - ES：单节点 → 多节点集群（至少 3 节点，分片数调整为 3，预装 IK 插件）

2. **应用服务集群化**：
   - 推荐服务打包为 Docker 镜像，部署多实例
   - 前置 Nginx / Spring Cloud Gateway 做负载均衡

3. **计算层集群化**：
   - Spark：`spark.master` 从 `local[*]` 改为 `yarn` 或 `k8s://...`
   - Flink：从本地模式改为 Standalone 集群或 Flink on YARN/K8s
   - 模型训练：从单机 GPU 改为分布式训练（DeepSpeed / Horovod）

4. **配置变更清单**：

## 八、技术风险与应对方案

### 8.1 核心风险点（修复后）

#### 风险 R-01：单机资源瓶颈导致性能指标不达标（已修复 P1-07）

| 维度 | 内容 |
|-----|------|
| 风险描述 | 单机 16GB 内存需同时运行多个组件，资源竞争可能导致 QPS 达不到 1000、响应时间超标 |
| 影响范围 | PERF-01（QPS ≥ 1000）、PERF-02（P50 < 80ms）、PERF-03（P99 < 200ms） |
| 发生概率 | 低（修复后） |
| 应对方案 | ① 严格按 6.2 节"理论 vs 实际"分配表限制各组件内存上限；② 压缩非关键组件内存（ES 512MB / Kafka 256MB / MongoDB 512MB / Redis 1GB）；③ 预留 2GB 系统余量；④ 离线窗口暂停 Flink 与模型推理服务，释放内存给 Spark；⑤ 召回通道并行执行（CompletableFuture）；⑥ 模型推理批量调用，减少 gRPC 往返；⑦ 缓存命中率优化至 ≥ 60% |
| 兜底方案 | 若单机确实无法达到 1000 QPS，在文档中明确标注单机实际 QPS，并说明集群化后可线性扩展 |

#### 风险 R-02：模型推理服务成为性能瓶颈（已修复 P1-06）

| 维度 | 内容 |
|-----|------|
| 风险描述 | DeepFM 模型推理涉及矩阵运算，单次批量推理可能超过超时阈值，导致排序降级 |
| 影响范围 | PERF-02/PERF-03、排序质量（降级后 CTR 下降） |
| 发生概率 | 低（修复后） |
| 应对方案 | ① ONNX Runtime 启用所有优化（`graph_optimization_level=ORT_ENABLE_ALL`）；② 推理服务使用多线程（`intra_op_num_threads=4`）；③ 批量推理（候选物品合并推理）；④ **三级降级链路**：DeepFM（80ms 超时）→ XGBoost（20ms 超时）→ 规则排序；⑤ 候选数量收紧至 200~300；⑥ 预测缓存 Key 含 modelVersion；⑦ 请求入口快照模型引用，避免热加载导致同批候选使用不同模型 |
| 兜底方案 | DeepFM 超时后自动降级为 XGBoost（5ms 内），再降级为规则排序，保证接口可用性 |

#### 风险 R-03：实时特征链路延迟超标（已修复 P1-02）

| 维度 | 内容 |
|-----|------|
| 风险描述 | Flink 窗口计算 + MongoDB 写入 + Redis 写入可能导致端到端延迟超过 5 秒 |
| 影响范围 | PERF-05（实时特征延迟 < 5 秒） |
| 发生概率 | 低（修复后） |
| 应对方案 | ① **改用 1 分钟滚动窗口 + AggregateFunction 增量聚合**，每窗口仅维护 3 个 long 计数器；② 1 小时聚合结果由 60 个 1 分钟窗口在应用层累加，Flink 不再维护 1 小时窗口；③ 统一事件时间语义 + BoundedOutOfOrdernessWatermarks（5 秒乱序容忍）；④ MongoDB 批量写入（100 条/1 秒）；⑤ Redis 异步写入（不阻塞 Flink 主流程）；⑥ Kafka 消费者 `fetch.min.bytes=1` 减少等待 |
| 兜底方案 | 若延迟超标，缩短窗口大小或减少聚合维度，优先保证核心行为（click）的实时性 |

#### 风险 R-04：离线任务无法按时完成（已修复 P2-08）

| 维度 | 内容 |
|-----|------|
| 风险描述 | 100 万行为数据 + 物品相似度矩阵计算可能耗时过长 |
| 影响范围 | PERF-06（离线任务按时完成） |
| 发生概率 | 低（修复后） |
| 应对方案 | ① Spark 本地模式使用 `local[*]` 充分利用多核；② 相似度计算先过滤低频物品（交互次数 < 5）；③ 使用 DataFrame 而非 RDD；④ 物品相似度只保留 Top-50；⑤ `spark.sql.shuffle.partitions=8`；⑥ **失败自动重试 2 次，间隔 5 分钟**；⑦ **重试仍失败发送 Webhook 告警**；⑧ 输出数据量校验，不达标标记失败；⑨ **支持 `--rerun {taskName}` 手动补跑** |
| 兜底方案 | 若超时，优先保证用户长期画像任务（推荐链路依赖），相似度矩阵可延长至 04:00 前完成 |

### 8.2 兼容性风险

#### 风险 C-01：Spring Boot 3.x 与中间件客户端版本不兼容

| 维度 | 内容 |
|-----|------|
| 风险描述 | Spring Boot 3.2 依赖的 Spring Data Elasticsearch 5.2、Spring Data MongoDB 4.2 等版本需与中间件严格对齐 |
| 影响范围 | 服务启动失败、运行时异常 |
| 发生概率 | 低 |
| 应对方案 | ① 严格按 1.3 节兼容性矩阵选择版本；② `@PostConstruct` 健康检查验证所有中间件连接；③ `pom.xml` 通过 `dependencyManagement` 统一管理版本；④ 开发环境先完成一次全链路联调验证 |
| 兜底方案 | 遇到版本冲突时，以 Spring Boot 3.2 BOM 管理的版本为准，升级中间件至兼容版本 |

#### 风险 C-02：ONNX 模型导出与推理兼容性

| 维度 | 内容 |
|-----|------|
| 风险描述 | XGBoost 2.0 和 PyTorch 2.1 导出的 ONNX 模型可能使用较高 opset，ONNX Runtime 1.16 可能不支持某些算子 |
| 影响范围 | 模型加载失败、推理结果错误 |
| 发生概率 | 中 |
| 应对方案 | ① XGBoost 导出 `target_opset=15`；② PyTorch 导出 `opset_version=17`；③ 导出后立即用 ONNX Runtime 加载验证（`onnx.checker.check_model` + 推理测试）；④ 模型服务启动时验证所有 active 模型可正常加载；⑤ 保留 PMML 作为备选导出格式 |
| 兜底方案 | 若 ONNX 兼容性问题无法解决，模型推理服务改为直接加载 XGBoost（Python 包）和 PyTorch 模型（`torch.load`） |

#### 风险 C-03：Windows 与 Linux 环境差异

| 维度 | 内容 |
|-----|------|
| 风险描述 | 开发环境以 Windows 为主，Spark/Flink/Kafka 等组件在 Windows 上可能存在兼容性问题 |
| 影响范围 | 本地开发环境搭建困难 |
| 发生概率 | 中 |
| 应对方案 | ① 优先使用 Docker Compose 部署中间件（跨平台一致）；② Spark/Flink 可在 WSL2 中运行；③ Windows 下运行 Spark 需安装 `winutils.exe`；④ 文件路径使用 Java NIO 的 `Path` 接口；⑤ 测试环境使用 Linux |
| 兜底方案 | 若 Windows 环境问题过多，切换至 WSL2 Ubuntu 22.04 作为开发环境 |

#### 风险 C-04：GPU 不可用时训练耗时超标

| 维度 | 内容 |
|-----|------|
| 风险描述 | 基线要求模型训练单次 ≤ 4 小时（CPU）/ ≤ 1 小时（GPU），若无 GPU，DeepFM 训练可能超过 4 小时 |
| 影响范围 | 模型训练效率、迭代速度 |
| 发生概率 | 中 |
| 应对方案 | ① 训练数据量控制（100 万行为，训练样本约 50 万）；② DeepFM 减少嵌入维度和隐藏层大小；③ Early Stopping（patience=3）；④ 特征预处理向量化；⑤ CPU 训练时启用多线程（`torch.set_num_threads(8)`）；⑥ 训练时关闭 Flink + 模型推理 + ES，释放内存 |
| 兜底方案 | 若 CPU 训练超过 4 小时，在文档中明确标注实际耗时，并说明 GPU 环境下的预期耗时差异 |

#### 风险 C-05：ES IK 分词器与 Embedding 模型兼容性（新增，修复 P1-04 / P1-05）

| 维度 | 内容 |
|-----|------|
| 风险描述 | IK 分词器版本必须与 ES 严格对齐；text2vec-base-chinese 模型加载可能因 transformers 版本不一致失败 |
| 影响范围 | CORE-02（ES 检索召回）、语义召回 |
| 发生概率 | 中 |
| 应对方案 | ① IK 插件版本严格对齐 ES 8.11.0；② Docker 自定义镜像预装 IK；③ text2vec 模型在 Python 推理服务启动时加载并 warmup；④ 提供 IK 降级方案（standard 分析器）；⑤ Embedding 服务不可用时降级为纯文本检索 |
| 兜底方案 | IK 失败用 standard；text2vec 失败可临时关闭语义检索分支，仅保留文本检索 |

### 8.3 性能风险

#### 风险 P-01：MongoDB 用户画像查询慢（已修复 P1-01）

| 维度 | 内容 |
|-----|------|
| 风险描述 | 用户画像文档较大，高并发查询可能超过 5ms |
| 影响范围 | PERF-02（特征组装阶段耗时） |
| 发生概率 | 低（修复后） |
| 应对方案 | ① `userId` 唯一索引；② **画像缓存拆分**：长期画像 TTL 300s、短期画像 TTL 5s，分别缓存；③ 应用层加权融合（短期 0.6 / 长期 0.4）；④ 投影查询；⑤ MongoDB 连接池 `maxConnectionPoolSize=20` |
| 兜底方案 | 若 MongoDB 查询慢，增加 Redis 缓存 TTL，减少回源 |

#### 风险 P-02：ES 向量检索延迟超标（已修复 P1-05）

| 维度 | 内容 |
|-----|------|
| 风险描述 | kNN 语义检索在 10000 物品规模下应 < 50ms，但 HNSW 索引参数不当可能导致延迟升高 |
| 影响范围 | CORE-02（ES 检索 < 50ms） |
| 发生概率 | 低（修复后） |
| 应对方案 | ① HNSW 参数 `m=16, ef_construction=100`；② 查询时 `num_candidates=200`；③ 向量维度 128（PCA 降维后）；④ 物品数 10000+，全量扫描也可接受；⑤ **Embedding 由 text2vec-base-chinese 生成，模型已确定** |
| 兜底方案 | 若 kNN 延迟超标，语义检索改为离线预计算（物品-关键词相似度矩阵），ES 仅做文本检索 |

#### 风险 P-03：Kafka 消息丢失（已修复 P1-10 / P1-08）

| 维度 | 内容 |
|-----|------|
| 风险描述 | 基线要求 DATA-04 消息丢失率 = 0（at-least-once） |
| 影响范围 | DATA-04、实时特征准确性 |
| 发生概率 | 低（修复后） |
| 应对方案 | ① **统一生产者配置** `acks=all` + `enable.idempotence=true`；② 消费者手动提交偏移量；③ Flink Checkpoint 与 Kafka 偏移量联动；④ **行为明细 eventId 唯一键**保证写入幂等；⑤ **短期画像 `$set` 覆盖写**保证幂等；⑥ **Redis ZADD 统一使用**（不使用 INCR）；⑦ **本地文件缓冲兜底**：Kafka 不可用时事件写入 `buffer/behavior/{date}.log`，恢复后批量重放；⑧ **端到端计数校验**：每 5 分钟对比 Kafka 生产端计数、Flink 处理计数、MongoDB 写入计数，偏差超过 0.1% 告警 |
| 兜底方案 | 若发现消息丢失，行为采集接口的本地文件缓冲机制可保证事件不丢失 |

#### 风险 P-04：缓存击穿/雪崩（已修复 P1-09）

| 维度 | 内容 |
|-----|------|
| 风险描述 | 推荐结果缓存 TTL 集中过期可能导致缓存击穿 |
| 影响范围 | PERF-01/PERF-02、后端服务压力 |
| 发生概率 | 低（修复后） |
| 应对方案 | ① 缓存 TTL 加随机偏移（60s ± 10s）；② 热点 Key 使用互斥锁（Redis SETNX）；③ **分层 TTL**：高频用户 10s / 普通用户 60s / 兜底 120s；④ **热点预缓存机制**：后台异步预刷新高频用户推荐结果；⑤ **Zipf 压测模型**：2000 高频用户模拟真实场景；⑥ 后端服务限流（Resilience4j） |
| 兜底方案 | 缓存大面积失效时，启用降级策略（返回热门物品兜底） |

### 8.4 应对方案汇总

| 风险编号 | 风险名称 | 风险等级 | 核心应对措施 | 状态 |
|---------|---------|---------|------------|------|

| R-04 | 离线任务超时 | 中 | 低频过滤 + DataFrame 优化 + 自动重试 + 手动补跑 | 已修复 P2-08 |
| C-01 | 中间件版本不兼容 | 中 | 严格版本矩阵 + BOM 管理 + 启动健康检查 | 已有方案 |
| C-02 | ONNX 兼容性 | 中 | 固定 opset + 导出即验证 + PMML 备选 | 已有方案 |
| C-03 | Windows/Linux 差异 | 中 | Docker Compose + WSL2 + 跨平台路径处理 | 已有方案 |

| **C-05** | **IK/Embedding 兼容性** | **中** | **严格版本对齐 + Docker 自定义镜像 + 降级方案** | **新增，已修复 P1-04 / P1-05** |

**风险等级定义**：
- 高：可能导致核心指标不达标或服务不可用，必须在开发阶段解决。
