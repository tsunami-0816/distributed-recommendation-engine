## 一、评审综述

本次评审覆盖技术选型、分层架构、核心业务链路、数据模型、接口规范、部署架构、监控运维共 7 个维度，对照项目基线的 10 项核心模块（CORE-01~CORE-10）、7 项性能指标（PERF-01~PERF-07）、4 项数据指标（DATA-01~DATA-04）逐项核验。

整体架构分层清晰，技术选型符合基线约束，核心链路（召回→排序→缓存）设计完整，降级策略覆盖全面。但在**资源配置一致性、实时链路设计、特征工程保障、搜索召回落地性**等方面存在需修正的问题。

#### P0-01：Spark 内存配置与单机资源分配硬冲突，离线计算链路无法启动

**问题描述**：
架构文档 2.5.2 节明确配置 `spark.driver.memory=4g`、`spark.executor.memory=4g`（本地模式即 driver 内存），但 6.1 节资源分配表中 Spark 仅分配 **1 GB**。同时，16 GB 总内存已被其余 9 个组件全部分配完毕（OS 2G + MySQL 1G + MongoDB 2G + Redis 2G + ES 2G + Kafka 1G + Flink 1G + 推荐服务 3G + 模型推理 1G = 16G），无额外空间支撑 Spark 的 4GB 需求。

**影响范围**：
- 全部 4 个离线 Spark 任务（物品热度统计、用户长期画像、物品相似度矩阵、训练样本构建）启动即 OOM 或无法分配内存
- ItemCF 召回（CORE-01）依赖物品相似度矩阵 → 断供
- 用户画像召回（CORE-01）依赖长期画像 → 断供
- 热门趋势召回（CORE-01）依赖热度统计 → 断供
- 模型训练（CORE-03/CORE-04）依赖训练样本 → 无法训练
- 4 路召回中 3 路数据断供，核心推荐链路质量严重退化，ALG-01（CTR 提升 ≥22%）、ALG-04（召回覆盖率 ≥85%）肯定不达标

**严重等级**：P0（符合定义第 1 条：核心业务链路数据断供；第 3 条：配置参数硬冲突无法落地）

**修改建议**：
1. **统一内存配置**：将 6.1 节资源分配表中 Spark 运行时内存从 1GB 调整为 **4GB**，与 `spark.driver.memory` 对齐
2. **重新核算总内存**：16GB 无法同时支撑所有组件 + Spark 4GB，需采取以下任一方案：
   - 方案 A（推荐）：离线任务运行时**暂停 Flink TaskManager 和模型推理服务**（离线任务在凌晨 00:30-02:00 运行，此时无实时推荐流量压力），释放约 2GB 空间；同时将 ES 从 2GB 降至 1GB、Kafka 从 1GB 降至 512MB，凑出 4GB 给 Spark
   - 方案 B：将基线硬件最低配置从 16GB 上调至 **24GB**，并在基线说明书中同步变更（需走基线变更流程）
3. **明确服务启停策略**：在部署手册中增加"离线任务运行时的服务启停编排"章节，明确哪些服务可以暂停、暂停顺序、恢复顺序
4. **Spark 配置修正**：本地模式下 `spark.executor.memory` 无效（本地模式所有任务运行在 driver JVM 中），应删除该配置避免误导，仅保留 `spark.driver.memory=4g`

#### P1-01：用户画像缓存失效策略与实时更新频率存在根本性矛盾，缓存命中率趋近于零

**问题描述**：
2.4.4 节规定 Flink 实时更新短期画像后"同时失效 Redis 缓存"，用户画像缓存 Key 为 `user:profile:{userId}`，TTL 300 秒。但 Flink 按 10 秒滑动步长持续更新短期画像，意味着**同一用户的画像缓存每 10 秒就被失效一次**，刚写入的缓存立即被删除，实际命中率趋近于 0。而 2.4.3 节又将用户实时短期特征的缓存 TTL 设为 5 秒，两套缓存机制重叠且互相冲突。

**影响范围**：
- 每次推荐请求均回源 MongoDB 读取用户画像，特征组装阶段（预算 <15ms）耗时增加
- 1000 QPS 下 MongoDB 读压力骤增（每秒约 1000 次画像文档查询，文档 2~5KB）
- PERF-02（P50 <80ms）、PERF-01（≥1000 QPS）存在不达标风险
- Redis 缓存层设计失效，与 PERF-07（缓存命中率 ≥60%）目标矛盾

**严重等级**：P1

**修改建议**：
1. **拆分画像缓存**：将 `user:profile:{userId}` 拆为两个 Key：
   - `user:profile:long:{userId}`：仅缓存长期画像，TTL 300 秒，离线任务更新时失效
   - `user:profile:short:{userId}`：缓存短期画像，TTL 5 秒，不主动失效（靠短 TTL 自动过期）
2. **应用层融合**：推荐请求时分别读取长期画像缓存和短期画像缓存，在内存中加权融合（短期 0.6 / 长期 0.4），避免全量画像缓存被频繁失效
3. **删除 Flink 中的画像缓存失效逻辑**：Flink 更新 MongoDB 后不再调用 Redis DEL，短期画像靠 5 秒 TTL 自然过期

#### P1-02：Flink 实时聚合使用 ListState 全量窗口计算，与"增量聚合"描述矛盾，实时特征延迟存在超标风险

**问题描述**：
3.2 节 `RealtimeFeatureAggregator` 明确使用 **ListState 存储窗口内事件** + ProcessingTimeTimer 触发计算，这是**全量窗口计算**模式（每次触发遍历整个 1 小时窗口的所有事件重新计数）。但同一节端到端延迟计算中声称"使用增量聚合，实际延迟 <1 秒"，风险 R-03 也建议"使用 AggregateFunction 而非全量窗口计算"。文档内部设计与描述自相矛盾。

此外，1 小时滑动窗口 + 10 秒步长意味着每个用户需维护 **360 个窗口状态**（3600s/10s），每个窗口存储该用户全部行为事件，单用户状态体积随行为频率线性增长，Checkpoint 体积和恢复时间不可控。

**影响范围**：
- PERF-05（实时特征端到端延迟 P99 <5 秒）存在不达标风险——全量窗口计算在高活跃用户上单次触发可能耗时数百毫秒至秒级
- Flink 状态后端内存压力大，Checkpoint 间隔 30 秒可能超时（配置超时 60 秒）
- 状态膨胀可能导致 Flink TaskManager OOM（仅分配 1GB 内存）

**严重等级**：P1

**修改建议**：
1. **改用增量聚合**：将 `RealtimeFeatureAggregator` 从 `KeyedProcessFunction + ListState` 改为 `KeyedWindow + AggregateFunction`（或 `ReducingState`），每个窗口只维护累加计数器（clickCount/viewCount/favoriteCount），不存储原始事件
2. **窗口优化**：1 小时滑动窗口用于实时特征过于笨重，建议改为：
   - 实时计数使用 **1 分钟滚动窗口**（延迟 <1 秒，满足实时性）
   - 1 小时聚合结果由 60 个 1 分钟窗口在应用层累加得到，不需要 Flink 维护 1 小时窗口
3. **统一事件时间语义**：3.2 节使用 ProcessingTimeTimer，但 1.2.3 节声明使用事件时间 + 5 秒乱序 Watermark。应统一为事件时间语义，使用 `BoundedOutOfOrdernessWatermarks`，避免乱序行为导致计数错误

#### P1-03：离线/在线特征一致性保障机制缺失，存在 Training-Serving Skew 风险

**问题描述**：
文档要求离线训练（Spark/Python）和在线推理（Java 特征服务）共用 `feature-definition.yml`，但**未定义任何特征一致性校验机制**。离线特征由 Spark SQL + Python 计算，在线特征由 Java 代码实时组装，两套独立实现极易产生细微差异：
- 归一化方式（min-max / z-score 的边界值处理）
- 缺失值填充策略（默认值 / 中位数 / 0）
- 类别特征编码（哈希编码的哈希函数、空值编码）
- 时间窗口的边界对齐（离线按天切片 vs 在线滑动窗口）

**影响范围**：
- ALG-05（XGBoost AUC ≥0.78、DeepFM AUC ≥0.80）离线达标但线上 AUC 显著下降
- ALG-01（CTR 提升 ≥22%）无法达标——模型在分布不一致的特征上推理，预测质量退化
- 问题隐蔽性强，上线后难以定位根因

**严重等级**：P1

**修改建议**：
1. **特征服务代码复用**：将特征计算逻辑封装为独立的 `feature-engine` 模块，提供 Java 和 Python 双语言实现（或使用 Java 编写特征服务，离线训练通过 Py4J/子进程调用），确保同一套计算逻辑
2. **增加特征一致性校验任务**：在每日训练样本构建后，随机抽取 1000 条样本，用在线特征服务重新计算特征，与离线训练样本的特征逐字段对比（余弦相似度 / 最大绝对误差），偏差超过阈值（如 1e-6）则告警并阻断模型发布
3. **特征定义强化**：`feature-definition.yml` 中每个特征必须明确声明：计算逻辑（伪代码）、归一化公式、缺失值处理、默认值、数据类型、取值范围，作为离线和在线实现的唯一权威依据

#### P1-04：Elasticsearch IK 分词器插件依赖未声明，索引创建将失败

**问题描述**：
4.4 节 ES 索引 `item_index` 的 mappings 中定义了自定义分析器 `ik_smart_analyzer`，使用 `ik_smart` tokenizer。但 **IK 分词器不是 Elasticsearch 内置插件**，需要单独下载安装（`elasticsearch-plugin install analysis-ik`）。技术选型总览（1.1 节）、部署架构（6.1 节）、兼容性矩阵（1.3 节）均未提及该插件依赖。

**影响范围**：
- CORE-02（ES 检索召回）验收受阻——索引创建时直接报错 `analyzer [ik_smart_analyzer] not found`，文本检索功能完全不可用
- 内容标签召回（CORE-01 中的 TagRecaller）依赖 ES `terms` query，虽然不依赖分词器，但索引创建失败会导致整个 ES 召回通道不可用
- 搜索场景（scene=search）完全不可用

**严重等级**：P1

**修改建议**：
1. **在技术选型中补充声明**：1.1 节选型总览增加一行"Elasticsearch IK 分词器 | analysis-ik 8.11.0 | 中文分词插件，ES 文本检索必需"
2. **在部署文档中增加安装步骤**：明确安装命令 `./bin/elasticsearch-plugin install https://get.infini.cloud/elasticsearch/analysis-ik/8.11.0`（或对应版本地址），以及验证方式 `GET /_analyze {"analyzer":"ik_smart","text":"测试分词"}`
3. **Docker Compose 增加自定义镜像**：如果使用 Docker Compose 部署 ES，需基于 `elasticsearch:8.11.0` 构建自定义镜像，在 Dockerfile 中预装 IK 插件
4. **增加降级方案**：如果 IK 插件安装失败，可临时使用 ES 内置的 `standard` 分析器（对中文按字切分，效果差但可运行），在文档中标注为降级方案

#### P1-05：物品/关键词 Embedding 生成方案完全缺失，语义召回（kNN）无法落地

**问题描述**：
4.4 节 ES 索引定义了 `embedding` 字段（dense_vector, dim=128, cosine 相似度，HNSW 索引），3.6 节搜索链路包含"ES 语义检索（可选）"，需要"关键词向量化（本地词向量模型 / 预计算 embedding）"。但全文**未说明**：
1. 物品 embedding 由什么模型生成？如何训练？输入是什么（物品标题/描述/标签）？
2. 查询关键词的 embedding 由什么模型生成？在线推理还是预计算？
3. 物品 embedding 和查询 embedding 是否在**同一向量空间**？（若不同源，cosine 相似度无意义）
4. 128 维是否足够？由什么模型导出？
5. 物品 embedding 何时更新？离线批量还是实时？

**影响范围**：
- CORE-02 中的"轻量语义召回"子功能无法实现——没有 embedding 数据，kNN 查询返回空结果
- 3.6 节搜索链路的语义检索分支为空操作，RRF 融合退化为纯文本检索
- ES 索引中的 `embedding` 字段和 HNSW 索引成为无用设计，浪费存储和索引构建时间

**严重等级**：P1

**修改建议**：
1. **明确 embedding 生成方案**（三选一，建议方案 A）：
   - 方案 A（推荐）：使用预训练中文词向量模型（如 `text2vec-base-chinese`，768 维→PCA 降维至 128 维），离线批量生成物品 embedding（输入=物品名称+描述+标签拼接文本），查询时在线调用同一模型生成关键词 embedding
   - 方案 B：使用 Word2Vec 在模拟行为数据上训练物品 embedding（Item2Vec），128 维，查询关键词通过物品标签匹配间接向量化
   - 方案 C：将语义召回标记为"暂不实现"，从 ES 索引中删除 `embedding` 字段和 HNSW 索引，3.6 节删除语义检索分支
2. **补充在线推理方案**：如果选择方案 A，需明确关键词 embedding 的在线生成方式——是在 Python 模型推理服务中增加 `/embed` 接口，还是在 Java 服务中集成轻量向量模型（如 `onnxruntime` + 导出的 text2vec ONNX 模型）
3. **明确更新机制**：物品 embedding 随离线任务每日更新（物品元数据变更时触发增量更新），写入 ES 的 `embedding` 字段

#### P1-06：DeepFM 推理性能与 50ms gRPC 超时存在冲突，A/B 实验组可能频繁降级

**问题描述**：
排序服务通过 gRPC 调用模型推理服务，超时硬编码为 **50ms**（`withDeadlineAfter(50ms)`），精排推理性能预算为 <30ms（含网络）。DeepFM 模型结构为 `hidden_dims=[256,128,64]`，推理时 batch_size = 候选物品数（200~500）。在 CPU 环境下（单机无 GPU 或 GPU 仅用于训练），DeepFM 批量推理 200~500 样本的耗时估算为 **15~35ms**，加上 gRPC 序列化/反序列化（2~5ms）、网络往返（本地回环 <1ms）、模型推理服务排队延迟，P99 很容易突破 50ms 超时阈值。

文档 2.4.2 节规定超时后"降级为规则排序（物品热度分）"，但风险 R-02 又说"XGBoost 可作为 DeepFM 超时时的降级模型"，两处降级策略不一致。

**影响范围**：
- A/B 实验中 DeepFM 实验组（CORE-04）如果频繁超时降级为规则排序，实验组 CTR 与对照组无显著差异，ALG-01（CTR 提升 ≥22%）无法验证
- 模型推理代理的本地预测缓存（TTL 10 秒）以 `featureHash` 为 Key，但用户实时特征每 5 秒变化，缓存命中率极低，无法有效减少推理调用
- PERF-03（P99 <200ms）受推理超时影响——50ms 超时后降级处理本身也需要时间

**严重等级**：P1

**修改建议**：
1. **统一降级策略**：明确 gRPC 超时后的降级链路为 **DeepFM → XGBoost（同服务内同步调用，<5ms）→ 规则排序**，而非直接降级为规则排序。XGBoost 推理极快，可保证排序质量不严重退化
2. **超时分层**：将 gRPC 超时从 50ms 调整为 **80ms**（DeepFM），同时在模型推理服务端设置推理超时 60ms；XGBoost 调用超时保持 20ms。整体精排阶段预算从 30ms 调整为 <50ms，总延迟预算相应调整（从 83ms 调整为 <100ms，仍在 P99 200ms 预算内）
3. **推理批量优化**：候选物品数量从 200~500 收紧为 **200~300**（召回合并后增加截断逻辑），减少 DeepFM 推理 batch size
4. **预测缓存修正**：`model:predict:{featureHash}` 的缓存 Key 应包含模型版本，且对实时特征变化不敏感的物品静态特征部分可单独缓存；或者直接移除该缓存（10 秒 TTL 在实时特征场景下价值有限）

#### P1-07：单机 16GB 内存整体超卖，1000 QPS 性能达标存在系统性风险

**问题描述**：
6.1 节资源分配表将 16GB 精确分配给 10 个组件，总和恰好 16GB，**零余量**。实际运行中：
- JVM 堆外内存（元空间、直接内存、线程栈）未计入——推荐服务 `-Xmx3g` 实际进程占用约 3.5~4GB
- Elasticsearch 除堆内存外还有 off-heap 内存（Lucene 段缓存、网络缓冲），实际占用约 1.5 倍堆内存
- 模型推理服务（Python + ONNX Runtime）加载 DeepFM 模型后内存占用可能超过 1GB
- 操作系统页面缓存、文件系统缓冲需要额外内存
- 无 GPU 时，CPU 训练 DeepFM 的 Python 进程需要 2~4GB 内存（完全未在分配表中体现）

**影响范围**：
- PERF-01（≥1000 QPS）、PERF-02（P50 <80ms）、PERF-03（P99 <200ms）在全组件同时运行时可能不达标——内存压力导致频繁 GC、swap 交换、CPU 飙高
- 模型训练（CORE-03/CORE-04）在 CPU 环境下可能 OOM，训练耗时超过 4 小时上限
- 风险 R-01 已识别但应对方案（资源配额限制）不足以解决零余量问题

**严重等级**：P1

**修改建议**：
1. **重新核算实际内存需求**：按"堆内存 × 1.3"估算各组件实际占用，制作"理论分配 vs 实际占用"对比表
2. **压缩非关键组件内存**：
   - Elasticsearch：`-Xms512m -Xmx512m`（10000 物品规模足够），释放 1GB
   - Kafka：`KAFKA_HEAP_OPTS=-Xmx256m`（单节点、低吞吐），释放 768MB
   - Flink：TaskManager 内存 512MB（本地模式、低并行度），释放 512MB
   - MongoDB：WiredTiger cache 512MB（10000 用户 + 100 万行为，数据量 <1GB），释放 1GB
3. **预留 2GB 系统余量**：压缩后总分配控制在 14GB 以内，预留 2GB 给操作系统、页面缓存和突发内存需求
4. **模型训练内存单独说明**：在部署文档中明确"模型训练时需关闭 Flink 和模型推理服务，释放约 1.5GB 给 Python 训练进程"，并给出 CPU/GPU 两种环境下的训练内存预估

---

#### P1-08：Flink at-least-once 语义下外部写入幂等性设计缺失，短期画像计数可能重复

**问题描述**：
文档 1.2.3 节明确采用"at-least-once + 消费端幂等去重"，但三个 Sink 的幂等设计均未落实：
1. **行为明细 MongoDB Sink**：`user_behavior` 集合未定义唯一键，Flink 从 Checkpoint 恢复后重复写入行为明细，导致行为计数偏高
2. **短期画像 MongoDB Sink**：如果采用 `$inc` 增量更新计数，重复执行会导致点击数/收藏数翻倍；如果采用全量覆盖写，则需要明确覆盖逻辑
3. **Redis 实时计数 Sink**：使用 `ZADD`（幂等）但文档 2.4.3 节又提到"实时行为计数（滑动窗口）"，如果使用 `INCR` 则非幂等

**影响范围**：
- 用户短期画像计数不准确，影响实时特征质量和排序效果
- 行为明细重复导致离线训练样本正样本比例偏高，模型训练偏差
- DATA-04（消息丢失率 =0）的 at-least-once 语义无法真正保证数据准确性

**严重等级**：P1

**修改建议**：
1. **行为明细幂等键**：在 `user_behavior` 集合增加 `eventId` 字段（由 `userId + itemId + actionType + eventTime` 哈希生成），建立唯一索引 `{eventId: 1}`，Flink 写入时使用 `insertOne` + 重复键忽略（`ordered=false` + 重复键异常捕获）
2. **短期画像覆盖写**：Flink 聚合结果使用 `$set` 全量覆盖 `shortTerm` 字段（而非 `$inc` 增量更新），重复执行结果相同，天然幂等
3. **Redis 计数幂等**：统一使用 `ZADD`（member=itemId+timestamp, score=timestamp），滑动窗口计数通过 `ZCOUNT` 计算，不使用 `INCR`
4. **增加端到端计数校验**：Flink 任务增加自定义 Metric，每 5 分钟对比 Kafka 生产端计数、Flink 处理计数、MongoDB 写入计数，偏差超过 0.1% 告警

---

#### P1-09：推荐结果缓存命中率 ≥60% 目标的可达性存疑，缓存 Key 设计未考虑用户访问分布

**问题描述**：
PERF-07 要求推荐结果缓存命中率 ≥60%，缓存 Key 为 `rec:result:{scene}:{userId}:{abGroup}`，TTL 60 秒。该设计隐含假设是**同一用户在 60 秒内重复访问**。但在实际场景中：
- 用户数 10,000+，如果用户访问均匀分布，每个用户平均访问间隔远大于 60 秒
- 压测时如果使用随机 userId 生成请求，缓存命中率将趋近于 0
- 60 秒 TTL 意味着每个用户每 60 秒最多贡献一次缓存命中，即使该用户每秒访问一次

文档未说明压测时的用户访问模型（固定用户集 vs 随机用户），也未说明 60% 命中率的测算依据。

**影响范围**：
- PERF-07（缓存命中率 ≥60%）可能无法达标
- 如果缓存命中率 <50%，则 P50 响应时间不再由缓存命中决定（之前分析 P50 <5ms 依赖命中率 >50%），PERF-02（P50 <80ms）达标压力增大
- 1000 QPS 下如果大部分请求缓存未命中，后端计算和存储压力骤增

**严重等级**：P1

**修改建议**：
1. **明确压测模型**：在性能压测方案中明确用户访问分布——使用 **Zipf 分布**（20% 的用户贡献 80% 的请求），固定 2000 个高频用户反复请求，模拟真实场景中的热点用户效应
2. **增加热点预缓存机制**：对高频用户（近 5 分钟访问次数 >阈值）的推荐结果进行**异步预刷新**——缓存过期前 10 秒由后台线程主动重新计算并更新缓存，用户请求始终命中缓存
3. **调整 TTL 策略**：对高频用户缓存 TTL 延长至 120 秒（配合异步刷新），低频用户保持 60 秒
4. **补充命中率测算**：在架构文档中增加缓存命中率的量化测算——基于 Zipf 分布、用户访问频率、TTL 时长，理论计算预期命中率，并与 60% 目标对比

---

#### P1-10：行为采集接口 acks=1 与高可用方案的本地缓冲机制未在主链路设计中落实

**问题描述**：
3.2 节行为采集接口明确"异步发送，acks=1，立即返回成功"，但 6.2 节高可用方案中 Kafka 不可用时的降级策略是"事件写入本地文件缓冲（`buffer/behavior/{date}.log`），Kafka 恢复后批量重放"。**主链路设计（3.2 节）完全没有提到本地文件缓冲机制**，如果实现时仅按 3.2 节做异步发送，Kafka 不可用时消息会直接丢失（异步发送失败后无兜底），与 DATA-04（消息丢失率 =0）矛盾。

此外，`acks=1` 在单节点 Kafka 下等同于 `acks=all`（单副本），但生产者配置（1.2.4 节）是 `acks=all`，行为采集接口单独使用 `acks=1`，两处配置不一致。

**影响范围**：
- DATA-04（Kafka 消息丢失率 =0）在 Kafka 故障场景下无法保证
- 实时特征管道（CORE-05）在 Kafka 恢复后丢失故障期间的行为数据，用户画像不完整
- 行为明细（DATA-02 保留 30 天）存在数据缺口

**严重等级**：P1

**修改建议**：
1. **统一生产者配置**：行为采集接口的 Kafka 生产者使用与全局一致的 `acks=all` + `enable.idempotence=true`，不要单独设置 `acks=1`
2. **落实本地缓冲机制**：在 `KafkaProducerService` 中增加本地文件缓冲逻辑——发送回调失败时，将行为事件序列化后追加写入 `buffer/behavior/{date}.log`，并启动一个后台线程（每 10 秒）检查 Kafka 可用性，恢复后批量重放缓冲文件中的事件
3. **缓冲文件管理**：缓冲文件按天滚动，保留 7 天（与 Kafka 保留期一致），重放成功后删除对应记录（或使用 offset 文件标记已重放位置）
4. **增加缓冲监控**：暴露 `behavior.buffer.size` 指标（缓冲文件中待重放的事件数），超过阈值（如 10000 条）告警

### P2 一般问题（8 项）

---

#### P2-01：A/B 分流哈希算法未指定，字符串拼接存在碰撞风险

**问题描述**：
3.5 节分流逻辑为 `hash(userId + experimentId) % 100`，但未指定哈希算法。若使用 Java `String.hashCode()`，存在分布不均和碰撞风险；且 `userId + experimentId` 直接拼接可能产生语义碰撞（如 `userId="u1", experimentId="exp2"` 与 `userId="u1e", experimentId="xp2"` 拼接结果相同）。

**影响范围**：A/B 实验分流比例偏差，实验结果统计显著性受影响

**严重等级**：P2

**修改建议**：使用 `MurmurHash3`（Guava `Hashing.murmur3_32()`），拼接时加入分隔符 `userId + ":" + experimentId`，并在文档中明确哈希算法和种子值

---

#### P2-02：模型推理服务 HTTP 端口文档内部不一致（8081 vs 8082）

**问题描述**：
1.2.9 节写"HTTP 健康检查 8081"，6.1 节端口分配表写"模型推理服务 HTTP 8082"，而 Flink Web UI 已占用 8081。若按 1.2.9 节实现会与 Flink 端口冲突。

**影响范围**：服务启动失败或健康检查端点不可用

**严重等级**：P2

**修改建议**：统一为 8082，修正 1.2.9 节的端口号

---

#### P2-03：推荐结果缓存 TTL 60 秒抵消实时特征更新效果

**问题描述**：
实时特征端到端延迟 <5 秒（PERF-05），但推荐结果缓存 60 秒才过期。用户点击某物品后，实时画像 5 秒内更新，但用户 60 秒内再次访问仍看到旧推荐结果，实时性设计被缓存抵消。

**影响范围**：用户体验——即时兴趣变化无法快速反映在推荐结果中

**严重等级**：P2

**修改建议**：对高活跃用户（近 1 分钟内有行为上报）的推荐结果缓存 TTL 缩短至 10 秒，或在行为上报时主动失效该用户的推荐结果缓存

---

#### P2-04：A/B 实验配置更新后已缓存分流结果不刷新

**问题描述**：
用户分流结果缓存 Key `ab:user:{userId}:{experimentId}`，TTL = 实验结束时间。如果实验运行中修改分流比例或实验组配置（通过管理后台），已缓存的用户分流结果不会更新，仍按旧配置分组。

**影响范围**：实验配置变更后生效延迟，实验数据混合新旧配置

**严重等级**：P2

**修改建议**：实验配置更新接口（`PUT /admin/ab/experiments/{experimentId}`）中增加逻辑：批量删除该 experimentId 下所有用户的分流缓存（使用 `SCAN` + `DEL`，或维护实验配置版本号，缓存 Key 中加入版本号）

---

#### P2-05：MongoDB 用户画像长期/短期并发更新的字段级原子性未明确

**问题描述**：
Flink 实时更新 `shortTerm` 字段，Spark 离线批量覆写 `longTerm` 字段，两者可能同时执行。文档未明确使用 `$set` 字段级更新还是整个文档替换。若使用整个文档替换，一方更新会覆盖另一方的字段。

**影响范围**：用户画像数据丢失（短期或长期画像被覆盖）

**严重等级**：P2

**修改建议**：明确 Flink 和 Spark 均使用 `$set` 操作符只更新目标字段（`shortTerm` / `longTerm`），不做全文档替换；在 `user_profile` 集合上建立 `userId` 唯一索引，使用 `upsert=true`

---

#### P2-06：模型热加载时批量推理过程中模型切换可能导致同批候选使用不同模型

**问题描述**：
模型推理服务使用 `AtomicReference` 原子切换活跃模型引用。但一次批量推理请求（200~500 候选）在执行过程中如果模型引用被切换，ONNX Runtime 的 `InferenceSession.run()` 不会中途切换模型（单次调用内使用同一个 session 引用），所以同批候选使用同一个模型。问题在于文档未明确这一行为，且旧模型保留 10 分钟用于回滚，但如果请求排队时模型切换，排队中的请求使用新模型还是旧模型未定义。

**影响范围**：A/B 实验中模型版本边界不清晰，少量请求可能使用非预期模型

**严重等级**：P2

**修改建议**：在模型推理服务中明确：请求进入推理队列时快照当前模型引用，排队和推理过程中始终使用该快照，不受热加载影响；在文档中补充这一行为说明

---

#### P2-07：接口限流组件选型未最终确定（Resilience4j vs Guava）

**问题描述**：
2.2 节接入层限流组件写"Resilience4j RateLimiter（或 Guava RateLimiter）"，两个二选一未最终确定。Resilience4j 支持熔断、重试、限流一体化且与 Spring Boot 3 集成好；Guava RateLimiter 轻量但功能单一。

**影响范围**：实现时选型困惑，限流行为可能不一致

**严重等级**：P2

**修改建议**：确定使用 **Resilience4j**（`resilience4j-spring-boot3`），与 Spring Boot 3 生态对齐，且后续可扩展熔断、重试能力；删除 Guava 选项

---

#### P2-08：离线任务调度缺少失败重试和告警的具体设计

**问题描述**：
3.3 节和 7.3.2 节定义了离线任务 DAG 调度（顺序执行，前序失败则后续不启动），但未说明：
1. 单个任务失败后是否自动重试？重试几次？间隔多久？
2. 任务失败后如何通知？（仅日志还是 Webhook 告警）
3. 手动补跑的流程是什么？
4. 任务部分成功（如相似度计算只完成 80% 物品）如何处理？

**影响范围**：离线任务失败后恢复依赖人工介入，PERF-06（02:00 前完成）在故障场景下无法保证

**严重等级**：P2

**修改建议**：在调度脚本中增加：每个任务失败后自动重试 2 次（间隔 5 分钟），重试仍失败则发送 Webhook 告警并终止 DAG；增加 `--rerun {taskName}` 参数支持单个任务手动补跑；任务完成后校验输出数据量（如相似度矩阵 ≥100,000 条），不达标则标记为失败

## 三、P0 问题修复后评审通过性判断

**结论：P0 修复后仍不能直接通过评审，需同步解决以下 3 个关键 P1 问题后方可通过：**

| 序号 | 问题编号 | 必须同步修复的理由 |
|-----|---------|-------------------|
| 1 | P1-04 | ES IK 分词器未声明 → CORE-02（ES 检索召回）无法验收，核心模块缺失 |
