## 一、项目核心目标

### 1.1 核心问题

在电商与内容平台场景下，用户面临**信息过载**导致的选择效率低下，平台面临**流量分发精准度不足**导致的点击率与停留时长瓶颈。现有通用推荐方案存在以下具体问题：

- 召回策略单一，无法覆盖用户多样化兴趣（长尾物品曝光不足）
- 排序模型特征维度有限，点击/转化预测精度低
- 用户行为反馈链路延迟高（分钟级甚至小时级），无法捕捉即时兴趣变化
- 搜索、推荐、广告三场景各自独立建设，算法与特征无法复用，研发成本高

### 1.2 业务价值

| 价值维度 | 具体描述 | 量化目标 |
|---------|---------|---------|
| 流量效率 | 提升用户点击意愿，降低无效曝光 | 推荐点击率（CTR）相对基线提升 ≥ 22% |
| 用户留存 | 延长用户单次访问停留时间 | 人均浏览时长相对基线提升 ≥ 16% |
| 工程复用 | 一套引擎支撑搜索、推荐、广告三场景 | 三场景共用召回层与排序层，场景差异化代码占比 ≤ 30% |
| 架构可扩展 | 单机伪分布式可平滑迁移至生产集群 | 核心代码零修改完成集群部署，仅修改配置文件 |

### 1.3 技术目标

构建一套**召回 + 排序两阶段**的分布式推荐引擎全链路，在单机伪分布式环境下完成端到端功能验证，核心算法逻辑与生产级架构保持一致，为后续集群化部署提供可直接复用的代码基线。

## 二、核心指标量化

### 2.1 算法效果指标

| 指标编号 | 指标名称 | 定义 | 基线值 | 目标值 | 验证方式 |
|---------|---------|------|-------|-------|---------|
| ALG-01 | 推荐点击率（CTR） | 推荐位点击数 / 推荐位曝光数 × 100% | 历史同期均值 | 相对基线提升 ≥ 22% | A/B 实验，实验组 vs 对照组，置信度 ≥ 95% |
| ALG-02 | 人均浏览时长 | 单次会话内用户累计停留页面时间（秒） | 历史同期均值 | 相对基线提升 ≥ 16% | A/B 实验，埋点日志统计 |
| ALG-03 | 转化率（CVR） | 推荐引导下单数 / 推荐位点击数 × 100% | 历史同期均值 | 相对基线不下降（≥ 基线值） | A/B 实验，订单日志关联 |
| ALG-04 | 召回覆盖率 | 召回结果中命中用户历史偏好类目的物品占比 | — | ≥ 85% | 离线评估，用户历史行为标签匹配 |
| ALG-05 | 排序模型 AUC | 排序模型在测试集上的 ROC-AUC | — | XGBoost ≥ 0.78；DeepFM ≥ 0.80 | 离线测试集评估，固定随机种子可复现 |
| ALG-06 | 长尾物品曝光占比 | 曝光物品中热度排名后 50% 物品的曝光量占比 | — | ≥ 20% | 曝光日志统计 |

### 2.2 系统性能指标

| 指标编号 | 指标名称 | 定义 | 目标值 | 验证方式 |
|---------|---------|------|-------|---------|
| PERF-01 | 单接口 QPS | 单机环境下推荐 API 每秒可处理请求数 | ≥ 1000 QPS | JMeter / wrk 压测，持续 5 分钟，错误率 = 0 |
| PERF-02 | 平均响应时间 | 推荐接口从请求到返回的平均耗时 | < 80 ms | 压测期间 P50 响应时间 |
| PERF-03 | P99 响应时间 | 99% 请求的响应时间上限 | < 200 ms | 压测期间 P99 统计 |
| PERF-04 | 集群扩展目标 | 横向扩展至生产集群后的 QPS 支撑能力 | ≥ 100,000 QPS | 架构评审 + 线性扩展系数验证（单机 QPS × 节点数 × 0.8） |
| PERF-05 | 实时特征更新延迟 | 用户行为发生到特征可被推荐链路使用的端到端延迟 | < 5 秒（单机）；< 3 秒（生产集群） | 行为埋点时间戳 vs 特征读取时间戳差值，采样 1000 条取 P99 |
| PERF-06 | 离线画像更新周期 | Spark 离线任务计算用户长期画像的完成周期 | T+1，每日 02:00 前完成 | 任务调度日志检查 |
| PERF-07 | 推荐结果缓存命中率 | Redis 中命中缓存的推荐请求占比 | ≥ 60% | 缓存访问日志统计 |

### 2.3 数据与存储指标

| 指标编号 | 指标名称 | 定义 | 目标值 | 验证方式 |
|---------|---------|------|-------|---------|
| DATA-01 | 用户画像标签维度 | 单用户画像包含的标签字段数量 | ≥ 50 个维度 | MongoDB 文档结构检查 |
| DATA-02 | 行为明细保留期 | 用户行为日志在 MongoDB 中的保留时长 | ≥ 30 天 | TTL 索引配置检查 |
| DATA-03 | 物品相似度矩阵规模 | 离线计算的物品两两相似度条目数 | ≥ 100,000 条 | Spark 输出文件行数统计 |
| DATA-04 | Kafka 消息丢失率 | 实时行为管道中的消息丢失比例 | = 0（at-least-once 语义） | 生产端计数 vs 消费端计数对比 |

## 三、项目范围界定

### 3.1 核心范围（必须做）

以下为项目交付必须包含的功能模块，缺一不可：

| 编号 | 模块 | 具体交付内容 | 验收标准 |
|-----|------|------------|---------|
| CORE-01 | 多路召回层 | 协同过滤召回、内容标签召回、用户画像召回、热门趋势召回，共 ≥ 4 路 | 每路召回可独立返回 ≥ 100 个候选物品；多路合并后去重 |
| CORE-02 | Elasticsearch 检索召回 | 单节点 ES 实现文本检索与轻量语义召回 | 支持关键词搜索召回，响应时间 < 50ms；索引物品数 ≥ 10,000 |
| CORE-03 | 精排模型 - XGBoost | 基于 XGBoost 的点击率预测模型 | 融合用户/物品/上下文 ≥ 30 维特征；AUC ≥ 0.78；支持本地 GPU 加速训练 |
| CORE-04 | 精排模型 - DeepFM | 基于 DeepFM 的点击率/转化率预测模型 | 融合用户/物品/上下文 ≥ 30 维特征；AUC ≥ 0.80；支持本地 GPU 加速训练 |
| CORE-05 | 实时特征计算管道 | Flink（本地模式）+ Kafka（单节点）实时处理点击、浏览、收藏行为 | 支持 ≥ 3 种行为类型；端到端延迟 < 5 秒；秒级更新用户画像标签 |
| CORE-06 | 用户画像存储 | MongoDB 存储用户画像标签与行为明细 | 画像标签 ≥ 50 维；行为明细保留 ≥ 30 天；支持按用户 ID 毫秒级查询 |
| CORE-07 | 缓存层 | Redis 缓存推荐结果与热点数据 | 推荐结果缓存 TTL 可配置；缓存命中率 ≥ 60% |
| CORE-08 | 离线计算层 | Spark（本地模式）离线计算用户长期画像与物品相似度矩阵 | T+1 每日更新；物品相似度 ≥ 100,000 条；用户长期画像 ≥ 20 维 |
| CORE-09 | 统一推荐 API | RESTful 接口，支持首页推荐、猜你喜欢、相关推荐 ≥ 3 种场景 | 单接口 ≥ 1000 QPS；平均响应 < 80ms；场景通过参数切换 |
| CORE-10 | A/B 实验框架 | 支持流量分流、实验组配置、效果指标对比 | 支持 ≥ 2 组并行实验；分流比例可配置（粒度 1%）；实验报告含 CTR/CVR/时长对比 |

### 3.2 配套范围（辅助做）

以下为提升项目完整性与可维护性的辅助工作，非核心交付但应包含：

| 编号 | 模块 | 具体内容 |
|-----|------|---------|
| AUX-01 | 数据模拟与构造 | 构造模拟用户行为数据（点击/浏览/收藏/转化），用于离线训练与联调测试，用户数 ≥ 10,000，物品数 ≥ 10,000，行为记录 ≥ 1,000,000 条 |
| AUX-02 | 特征工程管道 | 统一特征抽取与预处理模块，支持离线/实时特征对齐，特征定义配置化 |
| AUX-03 | 模型训练流水线 | 模型训练脚本化，支持数据加载 → 特征工程 → 训练 → 评估 → 模型导出全流程自动化 |
| AUX-04 | 监控与日志 | 关键链路日志埋点（请求 ID 全链路追踪）、接口耗时统计、异常告警基础框架 |
| AUX-05 | 部署文档 | 单机伪分布式环境部署手册、集群化迁移指南（配置变更清单） |
| AUX-06 | API 文档 | 基于 OpenAPI/Swagger 的接口文档，含请求/响应示例与错误码定义 |

### 3.3 排除范围（明确不做）

以下内容**不在本项目范围内**，后续需求变更需单独评审：

| 编号 | 排除项 | 排除理由 |
|-----|-------|---------|
| OUT-01 | 真实生产集群部署与运维 | 本项目定位为单机伪分布式环境验证，集群部署仅提供迁移指南，不实际搭建生产集群 |
| OUT-02 | 真实用户数据接入与隐私合规处理 | 使用模拟数据，不接入真实用户个人信息；不涉及 GDPR / 个人信息保护法合规改造 |
| OUT-03 | 推荐结果可解释性模块 | 不实现推荐理由生成、归因分析等可解释性功能 |
| OUT-04 | 多模态内容理解 | 不处理图片、视频、音频等非文本内容的特征提取与召回 |
| OUT-05 | 在线学习（Online Learning） | 模型更新为 T+1 离线批量更新，不实现参数级实时在线学习 |
| OUT-06 | 广告竞价与计费系统 | 广告场景仅复用推荐排序能力，不实现竞价、扣费、预算控制等广告专属功能 |
| OUT-07 | 移动端 SDK 与前端展示层 | 仅提供后端 API，不包含客户端 SDK、推荐位 UI 组件与前端渲染 |
| OUT-08 | 跨语言微服务治理 | 不引入服务网格（Service Mesh）、分布式事务、全链路压测平台等生产级治理组件 |
| OUT-09 | 冷启动专项优化 | 新用户/新物品冷启动使用通用热门兜底策略，不实现专门的冷启动算法（如 Bandit） |

## 四、约束条件

### 4.1 技术栈约束

| 层级 | 技术选型 | 版本要求 | 约束说明 |
|-----|---------|---------|---------|
| 后端服务 | Java + Spring Boot | Java 17+，Spring Boot 3.x | 推荐 API 服务必须基于 Spring Boot 构建，不得替换为其他语言/框架 |
| 离线计算 | Apache Spark | Spark 3.x（本地模式） | 仅使用本地模式，不搭建 Spark on YARN/K8s 集群 |
| 实时计算 | Apache Flink | Flink 1.17+（本地模式） | 仅使用本地模式，DataStream API 实现实时特征管道 |
| 消息队列 | Apache Kafka | Kafka 3.x（单节点 / KRaft 模式） | 单节点部署，不搭建多 Broker 集群 |
| 搜索引擎 | Elasticsearch | Elasticsearch 8.x（单节点） | 单节点部署，用于文本检索与轻量语义召回 |
| 缓存 | Redis | Redis 7.x（单节点） | 单节点部署，用于推荐结果与热点数据缓存 |
| 关系型数据库 | MySQL | MySQL 8.0 | 存储物品元数据、用户基础信息、实验配置等结构化数据 |
| 文档数据库 | MongoDB | MongoDB 6.x（单节点） | 存储用户画像标签与行为明细 |
| 算法模型 | Python + XGBoost + DeepFM | Python 3.10+，XGBoost 2.x，DeepFM（基于 TensorFlow/PyTorch） | 模型训练使用 Python，模型服务通过 PMML/ONNX 或自定义 RPC 供 Java 侧调用 |
| 模型加速 | 本地 GPU | CUDA 11.8+（如硬件支持） | 训练阶段优先 GPU 加速；无 GPU 时降级为 CPU 训练，但需在文档中标注训练耗时差异 |

### 4.2 部署环境约束

| 约束项 | 具体要求 |
|-------|---------|
| 部署模式 | 单机伪分布式：所有中间件（Kafka、Flink、Spark、ES、Redis、MongoDB、MySQL）均部署在同一台物理机/虚拟机上 |
| 操作系统 | Windows 10/11 或 Linux（Ubuntu 22.04 / CentOS 7+），开发环境以 Windows 为主 |
| 硬件最低配置 | CPU ≥ 8 核；内存 ≥ 16 GB；磁盘可用空间 ≥ 50 GB；GPU 可选（NVIDIA，显存 ≥ 4 GB） |
| 网络 | 全部服务通过 localhost / 127.0.0.1 通信，不涉及跨机网络调用 |
| 容器化 | 可选 Docker Compose 编排中间件，但非强制；不使用 Kubernetes |

### 4.3 资源约束

| 约束项 | 具体限制 |
|-------|---------|
| 人力 | 单人开发（全栈：后端 + 算法 + 数据工程） |
| 数据规模 | 模拟数据：用户 ≥ 10,000，物品 ≥ 10,000，行为记录 ≥ 1,000,000 条；不使用真实生产数据 |
| 计算资源 | 单机资源上限；模型训练单次完整训练耗时 ≤ 4 小时（CPU）/ ≤ 1 小时（GPU） |
| 第三方依赖 | 不依赖需付费的商业 API 或云服务；所有组件使用开源版本 |

### 4.4 时间约束

| 阶段 | 交付内容 | 建议周期 |
|-----|---------|---------|
| 阶段一：环境与数据 | 中间件部署、模拟数据生成、基础工程骨架 | 第 1 周 |
| 阶段二：召回层 | 多路召回实现、ES 检索召回、召回合并 | 第 2-3 周 |
| 阶段三：排序层 | 特征工程、XGBoost/DeepFM 训练与评估、模型服务化 | 第 4-5 周 |
| 阶段四：实时链路 | Kafka + Flink 实时特征管道、用户画像秒级更新 | 第 6 周 |
| 阶段五：API 与实验 | 统一推荐 API、A/B 实验框架、缓存层集成 | 第 7 周 |
| 阶段六：压测与交付 | 性能压测、效果验证、文档整理、集群迁移指南 | 第 8 周 |

> 注：以上为建议周期，实际以项目排期为准；本基线不设定硬性截止日期，但各阶段交付物须按顺序完成。

### 4.5 合规约束

| 约束项 | 具体要求 |
|-------|---------|
| 数据合规 | 全部使用模拟数据，禁止接入真实用户个人身份信息（PII）；模拟数据中的用户名、手机号等字段须为虚构 |
| 开源协议 | 使用的开源组件须兼容项目使用场景；引入新依赖前须检查 License（禁止 GPL 传染性协议） |
| 模型伦理 | 排序模型不得引入性别、种族、宗教等受保护属性作为直接特征；模拟数据中不包含此类敏感字段 |

## 六、基线变更管理

本说明书为项目基准文件，任何对以下内容的变更须经过正式评审并记录：

- 核心范围（CORE-01 ~ CORE-10）的增减
- 核心指标（ALG / PERF / DATA 系列）目标值的调整
- 技术栈选型的替换
- 排除范围的扩大或缩小

变更流程：提出变更申请 → 评估影响范围 → 更新本文档版本号 → 同步所有相关方。
