### 1.5 运维手册

#### 1.5.1 服务启停

**启动（生产环境）：**
```bash
cd recommendation-engine
mvn clean package -DskipTests
java -Xms1g -Xmx2g -XX:+UseG1GC -XX:MaxGCPauseMillis=200 \
  -jar target/recommendation-engine-1.0.0.jar \
  --spring.profiles.active=prod > logs/app.log 2>&1 &
echo $! > app.pid
```

**停止：**
```bash
kill $(cat app.pid)
# 或
pkill -f recommendation-engine-1.0.0.jar
```

**前端部署：**
```bash
cd recommend-admin
npm run build
# 将 dist/ 目录部署到 Nginx 静态文件服务器
```

#### 1.5.4 日志管理

| 日志文件 | 级别 | 滚动策略 | 保留期 | 说明 |
|---------|------|---------|-------|------|
| `logs/app.log` | INFO+ | 按天滚动，单文件500MB | 30天 | 应用主日志，异步写入，含traceId |
| `logs/error.log` | ERROR | 按天滚动 | 30天 | 仅错误日志，便于排查 |

**日志格式：** `timestamp | level | thread | logger | traceId | message`

**关键日志关键字：**
- 推荐请求：`[RECOMMEND] scene=xx userId=xx abGroup=xx modelVersion=xx`
- 缓存命中：`[CACHE] HIT key=xx duration=xxms`
- 缓存写入：`[CACHE] PUT key=xx ttl=xxs`
- 缓存失效：`[CACHE] INVALIDATE userId=xx keys=xx`
- 行为采集：`[BEHAVIOR] userId=xx itemId=xx actionType=xx eventId=xx`
- A/B分流：`[AB] userId=xx experimentId=xx group=xx`
- 模型降级：`[RANK] DEGRADED from=xx to=xx reason=xx`
- 限流触发：`[RATE_LIMIT] name=xx availablePermits=xx`

#### 1.5.5 常见故障排查

| 故障现象 | 可能原因 | 排查步骤 | 处理方案 |
|---------|---------|---------|---------|
| 推荐接口返回500 | 下游服务异常/空指针 | 1.查看error.log堆栈 2.检查Mock服务状态 | 修复代码或降级到规则排序 |
| 推荐接口返回429 | 触发限流 | 1.查看Prometheus available_permissions 2.分析流量来源 | 扩容或调整限流阈值 |
| 缓存命中率低 | 用户行为频繁导致失效/TTL过短 | 1.查看缓存命中/失效日志 2.检查用户访问频率 | 调整分层TTL策略或优化失效粒度 |
| 管理后台返回401 | API Key缺失或错误 | 1.检查请求头X-API-Key 2.核对配置中的Key | 使用正确的API Key |
| 响应时间突然升高 | GC停顿/缓存雪崩/下游超时 | 1.查看GC日志 2.检查缓存过期分布 3.查看下游耗时 | 优化JVM参数/加随机偏移/降级 |
| 服务启动失败 | 端口占用/配置错误/依赖缺失 | 1.查看启动日志 2.检查8084端口占用 3.校验application.yml | 释放端口/修正配置/安装依赖 |

### 3.2 核心问题与根本原因分析

#### 3.2.1 项目过程中发现的核心问题

**问题一：管理后台API鉴权完全缺失（P0-04）**

| 项目 | 内容 |
|-----|------|
| 问题描述 | 后端WebConfig.addInterceptors()为空，未注册任何鉴权拦截器，所有15个管理后台接口无任何访问控制 |
| 严重程度 | P0 致命（安全漏洞） |
| 发现阶段 | 第一轮全量测试 |
| 根本原因 | ① 开发时优先实现业务功能，鉴权作为"横切关注点"被延后；② 前端request.js已附加X-API-Key头，造成"鉴权已实现"的错觉；③ 缺少安全检查清单，未在联调阶段验证无权限访问的场景 |
| 修复方案 | 新增AuthInterceptor + 在WebConfig中注册拦截器，拦截/admin/**路径，校验X-API-Key |
| 修复结果 | ✅ 已修复，无Key返回401，正确Key返回200，OPTIONS预检放行 |
| 经验教训 | 安全功能必须与业务功能同步开发，不能作为"后续优化"；联调测试必须包含"未授权访问"场景 |

**问题二：A/B实验分流逻辑硬编码，实验配置完全不生效（P0-01）**

| 项目 | 内容 |
|-----|------|
| 问题描述 | RecommendationFacade.assignAbGroup()中experimentId固定为"default_exp"，分流比例固定50%/50%，未从AbExperimentService读取运行中的实验配置 |
| 严重程度 | P0 致命（核心功能不可用） |
| 发现阶段 | 第一轮全量测试 |
| 根本原因 | ① 开发顺序问题：先实现了推荐主链路的简化分流，后开发管理后台实验配置，两者未打通；② 缺少端到端集成测试，未验证"创建实验→启动实验→推荐分流生效"的完整链路；③ MockAbExperimentService与RecommendationFacade之间缺少依赖注入关联 |
| 修复方案 | RecommendationFacade注入AbExperimentService，从running状态实验读取trafficPercent和groupsConfig动态分流，实验组modelVersion生效 |
| 修复结果 | ✅ 已修复，实验配置可动态生效，分流确定性已验证 |
| 经验教训 | 跨模块功能必须在联调阶段做端到端验证，不能仅验证单个模块的单元功能；"接口已定义"不等于"功能已打通" |

**问题三：模型激活后不生效，活跃模型与配置脱节（P0-02）**

| 项目 | 内容 |
|-----|------|
| 问题描述 | MockModelManagementService.activateModel()仅更新内存中模型对象的status字段，但推荐链路通过properties.getModelInference().getActiveModel()读取配置文件中的固定值 |
| 严重程度 | P0 致命 |
| 发现阶段 | 第一轮全量测试 |
| 根本原因 | ① 配置来源不一致：管理后台修改内存store，推荐链路读取@ConfigurationProperties绑定的配置类，两者无同步机制；② 架构文档约定的"配置写入Redis支持热更新"未实现；③ 缺少"管理操作→推荐链路生效"的闭环验证 |
| 修复方案 | RecommendationFacade.getActiveModelVersion()从ModelManagementService读取active状态模型，无active时回退配置文件默认值 |
| 修复结果 | ✅ 已修复 |
| 经验教训 | 动态配置必须有统一的配置来源和同步机制；管理操作必须验证对业务链路的实际影响 |

**问题四：系统配置更新后不生效，热更新未实现（P0-03）**

| 项目 | 内容 |
|-----|------|
| 问题描述 | MockSystemConfigService.updateConfig()仅更新内存store，没有同步到RecommendProperties，管理后台修改缓存TTL等配置后运行中的系统仍使用旧值 |
| 严重程度 | P0 致命 |
| 发现阶段 | 第一轮全量测试 |
| 根本原因 | 与问题三同源：配置双源问题，缺少热更新同步机制 |
| 修复方案 | MockSystemConfigService.syncToProperties()实现8个配置项的热更新同步 |
| 修复结果 | ✅ 已修复 |
| 经验教训 | 同上，配置管理必须统一来源 |

**问题五：行为上报→缓存失效链路未实现（联调P-01）**

| 项目 | 内容 |
|-----|------|
| 问题描述 | BehaviorController.collect()仅调用behaviorCollectorService.collect()，未调用cacheService.invalidateByUser(userId)，用户行为无法实时影响推荐结果 |
| 严重程度 | 严重（阻断核心闭环） |
| 发现阶段 | 联调验证 |
| 根本原因 | ① 模块间调用关系遗漏：架构文档6.5节明确约定"行为触发失效"，但开发时BehaviorController未注入RecommendCacheService；② 联调测试覆盖了"行为上报成功"和"缓存命中"，但未覆盖"行为上报后缓存是否失效"的跨链路场景 |
| 修复方案 | BehaviorController注入RecommendCacheService，行为采集成功后调用invalidateByUser(userId) |
| 修复结果 | ✅ 已修复，实测失效后重新计算recallMs=5, rankMs=2 |
| 经验教训 | 联调测试必须设计跨链路一致性验证用例，不能仅验证单链路通断 |

**问题六：缓存按用户失效采用全表遍历，性能瓶颈（P1-05）**

| 项目 | 内容 |
|-----|------|
| 问题描述 | RecommendCacheService.invalidateByUser()使用cache.keySet().removeIf(key -> key.contains(userId))，每次调用遍历整个缓存Map |
| 严重程度 | P1 严重（性能） |
| 发现阶段 | 第一轮全量测试（代码走查发现） |
| 根本原因 | ① 实现时追求简单，未考虑生产环境缓存规模；② 缺少性能意识，未评估O(n)算法在百万级缓存下的影响；③ 单机Mock环境缓存量小，问题不明显 |
| 修复方案 | 维护userId→cacheKeys的反向索引（userKeyIndex），失效时只遍历该用户的缓存key，O(1)查找 |
| 修复结果 | ✅ 已修复 |
| 经验教训 | 代码走查必须关注算法复杂度，特别是被高频调用的方法；单机环境可接受的实现不一定适用于生产环境 |

**问题七：曝光埋点同步阻塞推荐响应（P1-04）**

| 项目 | 内容 |
|-----|------|
| 问题描述 | RecommendationFacade.recommend()在返回响应前同步调用behaviorCollectorService.trackImpression()，pageSize=50时50次循环计算和日志输出阻塞响应 |
| 严重程度 | P1 严重（性能） |
| 发现阶段 | 第一轮全量测试（代码走查发现） |
| 根本原因 | ① 架构文档明确要求"异步发送曝光埋点"，但实现时遗漏了@Async注解；② 启动类未添加@EnableAsync；③ 缺少性能测试验证pageSize较大时的响应时间 |
| 修复方案 | 添加@EnableAsync + trackImpression方法标注@Async |
| 修复结果 | ✅ 已修复 |
| 经验教训 | 架构文档中的异步/非阻塞约定必须在代码走查时重点核对 |

**问题八：仪表盘统计数据全部计算错误（P1-01）**

| 项目 | 内容 |
|-----|------|
| 问题描述 | DashboardAdminController.getDashboardStats()中QPS公式错误（实际等于1/mean(seconds)）、缓存命中率用缓存条目数除以总请求数、P99使用Timer.max()而非分位数 |
| 严重程度 | P1 严重（数据错误） |
| 发现阶段 | 第一轮全量测试 |
| 根本原因 | ① 对Micrometer Timer的API理解不准确，max()返回的是历史最大值而非分位数；② 指标计算公式未经过评审，直接编写；③ 缺少"指标计算正确性"的测试用例 |
| 修复方案 | QPS=totalRequests/uptimeSeconds，缓存命中率=命中次数/总请求次数，P99=Timer.percentile(0.99)，从业务计数器准确获取 |
| 修复结果 | ✅ 已修复，实测QPS=1.36/平均延迟=9.16ms/P99=22ms/命中率=0.645均为真实计算 |
| 经验教训 | 监控指标的计算公式必须经过评审和验证，"能返回数字"不等于"数字正确" |

#### 3.2.2 根本原因归纳

| 根本原因类别 | 涉及问题 | 占比 | 改进方向 |
|------------|---------|------|---------|
| 跨模块集成未打通 | P0-01(A/B分流)、P0-02(模型激活)、P0-03(配置热更新)、联调P-01(缓存失效) | 50% | 加强端到端集成测试，建立"管理操作→业务链路生效"的闭环验证清单 |

### 3.4 流程改进建议

#### 3.4.1 开发流程改进

| 改进项 | 当前问题 | 改进建议 | 预期效果 |
|-------|---------|---------|---------|
| 跨模块集成同步开发 | 先单模块开发后集成，导致集成问题后期集中爆发（4项P0问题中有3项是集成问题） | 采用"接口先行+联调驱动"模式：先定义模块间接口契约，再并行开发，每完成一个模块立即与依赖模块联调 | 集成问题提前暴露，减少后期修复成本 |
| 安全功能同步开发 | 鉴权作为"后续优化"被延后，导致P0安全漏洞 | 安全功能（鉴权/权限/数据校验）必须与业务功能同步开发，纳入DoD（完成定义） | 避免安全漏洞流入测试和生产 |
| 端到端测试用例先行 | 联调测试缺少跨链路一致性验证用例，导致"行为→缓存失效"等问题遗漏 | 在需求分析阶段就设计端到端测试用例，特别是跨模块链路的闭环验证用例 | 提高测试覆盖率，减少遗漏 |
| Mock实现标注机制 | Mock实现与真实实现边界不清晰，容易造成"功能已实现"的错觉 | 所有Mock类必须在类注释中标注"Mock实现，生产环境需替换为Xxx真实实现"，并在架构文档中列出Mock清单 | 明确交付边界，避免误解 |
| 代码走查检查清单 | 代码走查关注功能正确性，对性能/异步约定/算法复杂度关注不足 | 建立代码走查检查清单，包含：算法复杂度、异步注解、配置来源一致性、线程安全、异常处理、日志规范 | 提高代码质量，减少性能和设计问题 |

#### 3.4.2 测试流程改进

| 改进项 | 当前问题 | 改进建议 | 预期效果 |
|-------|---------|---------|---------|
| 性能测试前置 | 性能测试在最终验收阶段才执行，且因缺少压测工具未做持续压测 | 在开发阶段就进行基本性能验证（接口响应时间、缓存命中耗时），预发布环境执行JMeter持续压测 | 性能问题提前发现 |
| 指标计算正确性测试 | 仪表盘指标计算错误未被及时发现 | 对监控指标的计算公式编写单元测试，验证输入输出正确性 | 避免"能返回数字但数字错误" |
| 安全测试纳入必测 | 未执行SQL注入/XSS/越权访问等安全测试 | 上线前必须执行安全扫描，至少覆盖：越权访问、SQL注入、XSS、敏感信息泄露 | 避免安全漏洞上线 |
| 异常注入测试 | 三级降级链（DeepFM→XGBoost→规则）未实际触发验证 | Mock服务支持模拟超时和异常，验证降级链是否正确触发 | 确保降级机制有效 |
| 并发测试 | 未执行多线程并发测试，缓存并发更新/A/B分流并发等场景未验证 | 预发布环境执行并发测试，重点验证缓存并发、配置更新并发、行为上报并发 | 发现线程安全问题 |

#### 3.4.3 文档流程改进

| 改进项 | 当前问题 | 改进建议 | 预期效果 |
|-------|---------|---------|---------|
| Mock交付边界明确化 | 基线定义了10个核心模块，但实际交付以Mock为主，边界不够清晰 | 在交付文档中明确列出"已真实实现"和"Mock实现"的模块清单，以及Mock替换为真实实现的工作量评估 | 避免交付范围误解 |
| 部署文档实战验证 | 部署文档基于编写时的理解，未经过"从零开始按文档部署"的实战验证 | 交付前安排新人按部署文档从零搭建环境，记录遇到的问题并修正文档 | 确保部署文档可操作性 |
| 运维手册持续更新 | 运维手册在交付时编写，后续配置变更可能未同步更新 | 建立运维手册维护机制，每次配置变更/架构调整后同步更新运维手册 | 保持运维手册时效性 |

#### 3.4.4 项目管理改进

| 改进项 | 当前问题 | 改进建议 | 预期效果 |
|-------|---------|---------|---------|
| 里程碑评审机制 | 项目周期短（2天），缺少阶段性评审，问题在最终测试集中爆发 | 即使是短周期项目，也应设置"开发完成→联调→测试→验收"四个里程碑，每个里程碑有明确的准入准出标准 | 问题分阶段暴露和修复 |
| 风险登记与跟踪 | 项目风险（如Mock实现的局限性、压测工具缺失）未显式登记和跟踪 | 建立风险登记册，识别风险、评估影响、制定应对措施、定期跟踪 | 主动管理风险，减少意外 |
| 验收标准可测化 | 部分验收标准（如CTR提升≥22%）在Mock环境无法验证，缺少替代验证方案 | 对无法在当前环境验证的验收标准，明确标注"待X环境验证"，并制定验证计划和责任人 | 避免验收标准悬空 |
