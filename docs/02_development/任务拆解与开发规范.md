## 四、开发规范

### 4.1 代码规范

#### 4.1.1 Java代码规范

| 维度 | 规范 |
|-----|------|
| **代码风格** | 遵循Google Java Style，缩进4空格，行宽120字符，IDE安装CheckStyle/Spotless插件自动格式化 |
| **JDK版本** | Java 17 LTS，使用var局部变量类型推断（仅限简单明确场景），使用switch表达式，使用文本块（JSON/SQL） |
| **Spring Boot** | 3.2.x，构造器注入（@RequiredArgsConstructor），禁止@Autowired字段注入，配置类使用@ConfigurationProperties，开启虚拟线程spring.threads.virtual.enabled=true |
| **异常处理** | 自定义BusinessException继承RuntimeException，全局@RestControllerAdvice统一处理，禁止吞异常（catch后必须记录日志或重新抛出），禁止catch (Exception e) { e.printStackTrace(); } |
| **空值处理** | 使用Optional处理可能为null的返回值，方法参数使用@NonNull/@Nullable注解（Jakarta Annotation），禁止返回null集合（返回空集合Collections.emptyList()） |
| **并发** | 使用CompletableFuture异步编排，使用虚拟线程（Thread.ofVirtual()），共享状态使用AtomicReference/ConcurrentHashMap，禁止自己创建线程池（使用Spring管理的ThreadPoolTaskExecutor） |
| **日志** | SLF4J + Logback，使用占位符{}而非字符串拼接，日志级别：ERROR（系统错误/异常）/WARN（业务异常/降级）/INFO（关键流程节点）/DEBUG（详细调试信息），生产环境关闭DEBUG，敏感信息（手机号/身份证）脱敏 |
| **注释** | 类级Javadoc说明职责，公共方法Javadoc说明参数/返回/异常，复杂逻辑行内注释说明"为什么"而非"是什么"，禁止无意义注释（如// i++ 执行i加一） |
| **工具类** | 工具类使用final class + private构造器，静态方法，优先使用Apache Commons / Guava / Hutool已有工具，不重复造轮子 |
| **设计模式** | 策略模式（场景策略/召回通道）、工厂模式（策略工厂）、模板方法（离线任务基类）、代理模式（模型推理代理）、观察者（模型热加载监听），禁止过度设计 |

#### 4.1.2 Python代码规范

| 维度 | 规范 |
|-----|------|
| **代码风格** | 遵循PEP 8，缩进4空格，行宽100字符，使用black自动格式化，isort排序import |
| **Python版本** | Python 3.11，使用类型注解（Type Hints），使用dataclass定义数据类，使用f-string格式化 |
| **依赖管理** | requirements.txt固定版本，虚拟环境venv，关键依赖：torch==2.1, xgboost==2.0, onnxruntime==1.16, fastapi, uvicorn, grpcio, transformers>=4.30, py4j |
| **异常处理** | 自定义ModelInferenceException，try/except捕获具体异常类型，禁止裸except，异常必须记录日志（logging模块），资源使用with语句确保释放 |

## 七、风险管理

### 7.1 开发阶段风险

| 风险编号 | 风险描述 | 影响 | 概率 | 应对措施 |
|---------|---------|------|------|---------|
| D-01 | Spring Boot 3.x与中间件客户端版本不兼容 | 服务启动失败 | 中 | 严格按兼容性矩阵选择版本，@PostConstruct健康检查，dependencyManagement统一版本，开发环境先全链路联调 |
| D-02 | ONNX模型导出与推理兼容性问题 | 模型加载失败/推理错误 | 中 | XGBoost opset=15/PyTorch opset=17，导出后立即ONNX Runtime验证，模型服务启动验证active模型，保留PMML备选 |
| D-03 | Windows环境Spark/Flink/Kafka兼容性问题 | 本地开发环境搭建困难 | 中 | Docker Compose部署中间件，Spark/Flink在WSL2运行，Windows安装winutils.exe，文件路径用Java NIO Path |
| D-04 | Py4J双语言特征一致性调试困难 | 离线在线特征不一致 | 中 | 每日特征一致性校验任务（1000条对比），偏差超阈值阻断模型发布，详细差异明细输出，单元测试覆盖 |
| D-05 | 单机16GB内存资源竞争 | 性能指标不达标/OOM | 中 | 严格按资源分配表限制内存，离线窗口暂停Flink+模型推理，预留2GB系统余量，压缩非关键组件内存 |
| D-06 | 模型推理超时导致频繁降级 | 排序质量下降 | 中 | ONNX Runtime全优化+多线程，批量推理，候选收紧200~300，三级降级链路，超时阈值DeepFM 80ms/XGBoost 20ms |
| D-07 | Flink窗口聚合状态膨胀 | 实时计算OOM/延迟 | 低 | AggregateFunction增量聚合仅维护3个long计数器，不存储原始事件，状态体积恒定，1h聚合应用层累加 |
| D-08 | Kafka消息丢失/重复 | 数据准确性问题 | 低 | acks=all+幂等生产者+手动提交+eventId唯一键+$set覆盖写+ZADD幂等+本地缓冲兜底+端到端计数校验 |
